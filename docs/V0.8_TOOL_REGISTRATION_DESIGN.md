# v0.8 Tool Registration Design

This document defines the v0.8 MCP tool registration boundary before any
executable registration runtime is implemented. It is a design-only and
review-boundary document. It does not add a tool registry runtime, tool
discovery runtime, request dispatcher, protocol parser, transport runtime,
actual tool execution, local evidence reading, raw preview, dashboard
state-changing control, upload or import behavior, replay, active scan,
automatic ChatGPT handoff, tag changes, or GitHub Release changes.

## Purpose

- Consume the v0.8 backlog split, transport design, protocol handler design,
  and protocol negative test harness before tool registration work is
  considered.
- Separate executable tool registration from actual tool execution before any
  runtime callable surface exists.
- Keep tool metadata design separate from dispatcher, protocol parser,
  transport runtime, local evidence reader, raw preview, and state-changing
  dashboard behavior.
- Preserve the four-file AI input candidate boundary.

## Current v0.8 baseline

The current baseline includes the published v0.7 release, v0.8 backlog split,
v0.8 transport design-only boundary, v0.8 protocol handler design-only
boundary, and v0.8 protocol negative test harness. The gateway can process
local Burp export or collector output through redaction, verify, review, and
report flows, then present only the existing safe output bundle for human
review.

This tool registration design does not change that baseline. Candidate
findings remain candidates, risk remains draft, and final severity or scoring
remains manual.

## Tool registration design scope

This PR may define:

- Tool registration metadata boundaries.
- Registration and execution separation rules.
- Forbidden registration behavior categories.
- Required negative test categories for registration markers, runtime
  discovery, dispatch, execution, local evidence reading, raw preview, replay,
  active scan, external handoff, dashboard state-changing control, and upload
  or import behavior.
- Source-check requirements for later tool-registration-facing files.
- Review rules for later registration implementation PRs.

This PR may not add tool registration runtime code.

## Explicit non-goals

This design does not implement or approve:

- Executable tool registration.
- Tool registry runtime.
- Tool discovery runtime.
- Actual tool execution.
- Request dispatcher.
- Protocol parser.
- JSON-RPC parser.
- Transport runtime.
- Local evidence reader.
- Safe file body reader.
- Raw preview or raw download.
- Replay or active scan.
- Automatic ChatGPT handoff.
- Dashboard start or stop control.
- Upload or import action.
- Tag changes.
- GitHub Release changes.

## Allowed future registration boundary

A later tool registration implementation PR may be considered only after this
design is reviewed. That later PR must remain separate from actual tool
execution, request dispatch, protocol parsing, transport runtime, local
evidence reading, raw preview, dashboard state-changing control, upload or
import behavior, replay, active scan, and automatic handoff.

Allowed future registration behavior is limited to metadata that describes a
reviewed allowlist. Registration metadata is future design data only and is not
a runtime callable surface. It must not read local files, inspect safe file
bodies, preview raw data, replay traffic, start scans, or send output to an
external system.

## Forbidden registration behaviors

The tool registration design keeps the following behaviors blocked:

- Registering executable tools.
- Starting a runtime tool registry.
- Starting runtime tool discovery.
- Dispatching requests to tools.
- Executing any tool.
- Reading local evidence or safe file bodies.
- Previewing or downloading raw data.
- Registering replay or active scan behavior as a tool.
- Registering external handoff behavior as a tool.
- Starting or stopping dashboard services through a tool.
- Uploading or importing traffic through a tool.
- Parsing protocol messages or JSON-RPC requests.
- Starting transport runtime.

## Tool execution separation

Tool registration and actual tool execution must remain separate PRs.
Registration metadata is future design data only; it is not runtime callable
surface.

This design excludes:

- Tool call dispatch.
- Local file read behavior.
- Safe file body read behavior.
- Raw preview or raw download behavior.
- Replay or active scan behavior.
- External handoff behavior.

Local file read, safe file body read, raw preview, replay, active scan, and
external handoff must not be registered as tools in this PR. Candidate findings
remain candidates, risk remains draft, and final severity or scoring remains
manual.

## Required approval conditions

A later registration implementation PR must show:

- The registration allowlist is reviewed and explicit.
- Registration remains separate from execution.
- Request dispatch remains blocked unless separately approved.
- Local evidence reading remains blocked unless separately approved.
- Raw preview or download remains blocked unless separately approved.
- Replay, active scan, and external handoff remain blocked unless separately
  approved.
- Failure and blocked responses remain raw-free.
- Rollback does not depend on moving release tags or changing GitHub Releases.

## Required negative tests

Any later implementation PR must include negative tests or source checks that
fail if the PR adds:

- Tool registration runtime markers before approval.
- Tool registry runtime markers before approval.
- Tool discovery runtime markers before approval.
- Tool execution markers.
- Dispatcher markers.
- Local evidence reader tool markers.
- Raw preview or raw download tool markers.
- Replay or active scan tool markers.
- External handoff tool markers.
- Dashboard state-changing tool markers.

## Source-check requirements

Before tool registration runtime is allowed, the registration-facing file list
must be declared in a fixture and covered by source-check tests. A future PR
must fail if a registration-facing file contains forbidden markers for runtime
registration, runtime discovery, request dispatch, tool execution, local
evidence reading, safe file body reading, raw preview, replay, active scan,
external handoff, dashboard state-changing control, upload or import behavior,
protocol parsing, or transport runtime without a separate reviewed approval.

## Security review requirements

Every later registration PR must state:

- Whether executable registration is included.
- Whether registration metadata can create a callable surface.
- Whether tool execution remains blocked.
- Whether request dispatch remains blocked.
- Whether local evidence reading remains blocked.
- Whether raw preview or download remains blocked.
- Whether replay, active scan, or external handoff remains blocked.
- Whether any dashboard state-changing control or upload/import action is
  included.
- How blocked responses remain raw-free.
- How rollback works without moving release tags.

If any answer expands beyond design, fixture, source-check, or metadata-only
planning, the work must be split into another PR.

## Rollback expectations

Rollback for this design-only PR is a documentation, fixture, and test revert.
A later implementation PR must include its own rollback section and must not
depend on moving release tags or changing GitHub Releases.

## Deferred decisions

- Whether read-only tool contract planning should be completed before any
  registration implementation PR.
- Whether tool registration should stay fixture-only until transport and
  protocol skeleton planning is complete.
- Whether tool execution approval should require a separate threat model.
- Whether local evidence reader work should wait until a dedicated path
  traversal and raw-free error model is approved.
