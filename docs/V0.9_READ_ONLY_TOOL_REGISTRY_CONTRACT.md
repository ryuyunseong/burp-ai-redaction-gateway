# v0.9 Read-only Tool Registry Contract

## Purpose

This contract fixes the read-only tool registry boundary after the minimal
positive parser implementation. It is a contract-only planning record. It does
not implement a dispatcher, executable registry, tool execution, listener,
transport, local evidence reader, or file body reader.

## Current Baseline

- PR #142 merge commit: `7ba514e85eac5c340ce190126a0e556d8f7ed750`
- minimal blocked parser: merged
- minimal positive parser: merged
- dispatcher implementation: not implemented
- listener or transport runtime: not implemented
- executable tool registration: not implemented
- actual tool execution: not implemented
- local evidence reader: not implemented
- v0.9 tag: not created
- GitHub Release v0.9: not created

## Contract Scope

The contract defines metadata that a future read-only registry boundary may
expose to later approval packets. It only describes capability labels and
blocked side-effect flags. It does not turn parser output into an executable
tool call.

The contract consumes the parser boundary decisions and requires that parser
positive and negative behavior remain unchanged. Future dispatcher work must
receive separate explicit approval and must not be smuggled into this registry
contract.

## Explicit Non-goals

This contract does not approve:

- dispatcher implementation
- listener startup
- transport runtime
- executable tool registration
- actual tool execution
- local evidence reader
- safe file body reader
- raw preview or download
- replay or active scan
- dashboard state-changing control
- upload or import action
- automatic ChatGPT handoff
- positive parser behavior changes
- negative parser behavior changes
- v0.9 tag creation
- GitHub Release v0.9 creation

## Allowed Registry Metadata Fields

Only metadata-only fields are allowed in the v0.9 registry contract fixture:

- `registry_schema_version`
- `registry_contract_only`
- `read_only_capability_labels`
- `tool_execution_allowed`
- `dispatcher_invocation_allowed`
- `local_evidence_access_allowed`
- `raw_data_included`
- `manual_review_required`

The allowed fields are labels and booleans only. They must not contain target
identity, request or response bodies, credential values, local paths, command
strings, executable callbacks, or file contents.

The `tool_execution_allowed`, `dispatcher_invocation_allowed`, and
`local_evidence_access_allowed` fields are contract-stage false-only metadata
flags until a separate explicit approval changes their boundary. They are not
runtime approvals.

The `safe_file_inventory_metadata` capability label means verified output
inventory metadata only. It does not approve file body reads.

## Forbidden Registry Fields

The registry contract must not include fields that can carry raw traffic,
target identity, credential values, local paths, command execution metadata, or
runtime callback handles. Forbidden field names include:

- `raw_input`
- `raw_request`
- `raw_response`
- `target`
- `url`
- `domain`
- `ip`
- `credential`
- `token`
- `session`
- `local_path`
- `file_body`
- `command`
- `executable`
- `handler`
- `callback`
- `stack_trace`

## Parser Behavior Guard

The registry contract must not change parser behavior. A future implementation
PR that consumes this contract must prove:

- parser positive fixture behavior remains unchanged
- parser negative fixture behavior remains unchanged
- registry metadata is not built from untrusted input echo
- registry metadata does not trigger dispatcher invocation
- registry metadata does not trigger tool lookup, registration, or execution
- registry metadata does not read local evidence or safe file bodies

## Required Test Expectations

Tests for this contract must confirm:

- the contract document exists
- the contract fixture exists
- `registry_contract_only` is true
- registry, dispatcher, executable registration, tool execution, listener,
  transport, local evidence reader, raw preview, and handoff flags are false
- allowed registry metadata fields are metadata-only
- forbidden registry fields include raw, credential, target, path, executable,
  handler, callback, and stack trace categories
- parser positive and negative behavior unchanged requirements are present
- no raw traffic, credential value, target identifier, locator, local path, file
  body, stack trace body, or external sharing approval wording is present

## PR Split Requirements

The following work must remain separate PR scope:

- dispatcher approval packet
- dispatcher implementation

## Rollback Requirements

If registry contract work expands into dispatcher behavior, executable tool
registration, actual tool execution, listener or transport runtime, local
evidence access, file body reading, raw preview, replay, active scan, upload,
import, or automatic handoff, split or revert that scope.

The parser positive and negative behavior must remain unchanged during rollback.
The output bundle remains the same four AI candidate files.
