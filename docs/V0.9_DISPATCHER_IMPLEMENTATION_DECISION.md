# v0.9 Dispatcher Implementation Decision

This decision defines the candidate scope for a future dispatcher
implementation PR. It is documentation, fixture, and source-check planning only.
It does not implement dispatcher behavior, executable registration, actual tool
execution, local evidence reading, listener startup, or transport runtime.

## Purpose

- Fix the future dispatcher implementation boundary before source files exist.
- Require the dispatcher approval packet and negative fixture harness to be
  consumed by the implementation PR.
- Keep parser metadata, dispatcher decisions, registry metadata, and tool
  execution separated.
- Preserve raw-free blocked responses and raw-free audit metadata.

## Required Fixture Consumption

A future dispatcher implementation PR must consume:

- `tests/fixtures/v09_dispatcher_approval_packet.json`
- `tests/fixtures/v09_dispatcher_negative_cases.json`
- `tests/fixtures/v09_read_only_registry_dispatcher_boundary.json`

The implementation PR must continue respecting the protocol parser boundary and
registry dispatcher boundary. The thirteen dispatcher negative categories must
remain covered by implementation tests. Allowed response field drift and
forbidden echo class drift must fail tests.

## Dispatcher Implementation Candidate Scope

A future implementation PR may define a minimal dispatcher decision helper only
after the approval packet and negative fixture harness are consumed. That helper
may classify parser metadata as blocked or denied, but it must not register
tools, execute tools, read local evidence, read file bodies, start a listener,
or open transport runtime.

Capability labels from the read-only registry remain metadata labels. They are
not callback handles, handler names, commands, or executable registrations.

## Dispatcher Input Boundary

Future dispatcher input may accept only parser metadata that has already passed
the parser boundary. It must reject or block metadata that attempts to carry:

- raw traffic bodies
- credential, token, or session values
- target identifiers
- URL, domain, or IP values
- full local paths
- local evidence bodies
- safe file bodies
- callback handles
- handler names
- command strings
- tool results

Parser behavior must not change in the dispatcher implementation PR.

## Dispatcher Output Boundary

Future dispatcher output must preserve the allowed dispatcher output fields from
the approval packet:

- `status`
- `reason_code`
- `dispatcher_approved`
- `dispatcher_invocation_allowed`
- `tool_execution_allowed`
- `raw_data_included`
- `manual_review_required`
- `safe_message`

No other output field may be returned by a blocked or denied dispatcher path.

## Blocked Response Boundary

Blocked dispatcher responses must be raw-free metadata only. They must not echo
original parser input, raw traffic, credentials, target identifiers, local
paths, local evidence bodies, file bodies, callback handles, handler names,
command strings, stack traces, or tool results.

Every blocked response must keep dispatcher invocation and tool execution
disabled and must require manual review.

## Audit Boundary

Future dispatcher audit metadata may include only synthetic case labels, status
labels, reason codes, boolean boundary flags, and manual-review flags. It must
not include raw traffic, credentials, target identifiers, full local paths,
local evidence bodies, file bodies, handler names, callback handles, command
strings, or tool results.

## Source-check Requirements

The original decision PR did not add dispatcher implementation files. The
minimal helper follow-up adds only `burp_ai_redaction_gateway/mcp_dispatcher.py`
with source-check coverage. Source checks must keep executable registration,
tool execution, local evidence reading, file body reading, raw preview, replay,
active scan, listener startup, transport runtime, callback handles, handler
names, command strings, and automatic handoff out of scope unless a later
approval explicitly changes the boundary.

## Minimal Helper Follow-up

The v0.9 minimal dispatcher decision helper is implemented in
`burp_ai_redaction_gateway/mcp_dispatcher.py`. It produces only blocked raw-free
responses using the dispatcher approval packet allowed fields. It consumes the
approval packet, negative fixture, implementation decision, and registry
dispatcher boundary through tests.

The helper does not implement executable registration, actual tool execution,
local evidence reading, safe file body reading, raw preview or download, replay
or active scan, automatic ChatGPT handoff, listener startup, transport runtime,
parser behavior changes, output bundle changes, tag creation, or release
creation.

The helper `reason_code` is restricted to known dispatcher negative categories
and the fallback blocked reason.

After this helper, the next v0.9 safe-core candidate is release readiness.
