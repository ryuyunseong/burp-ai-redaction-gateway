# v0.8 Protocol Negative Test Harness

This document defines the v0.8 MCP protocol negative harness before any
protocol runtime is implemented. It is a planning and test-boundary document
only. It does not add an MCP protocol handler, JSON-RPC parser, protocol
message parser, schema validation runtime, request dispatcher, executable tool
registration, actual tool execution, transport runtime, socket behavior, local
evidence reading, raw preview, dashboard state-changing control, upload or
import behavior, replay, active scan, automatic ChatGPT handoff, tag changes,
or GitHub Release changes.

## Purpose

- Consume the v0.8 backlog split, transport design, and protocol handler
  design before protocol runtime work is considered.
- Fix malformed input, echo-forbidden, forbidden source marker, and
  blocked-response expectations as test inputs before implementation.
- Keep protocol negative tests separate from parser, dispatcher, tool
  registration, tool execution, transport runtime, and local evidence reader
  work.
- Preserve the four-file AI input candidate boundary.

## Current v0.8 baseline

The current baseline includes the published v0.7 release, v0.8 backlog split,
v0.8 transport design-only boundary, and v0.8 protocol handler design-only
boundary. The gateway can process local Burp export or collector output through
redaction, verify, review, and report flows, then present only the existing
safe output bundle for human review.

This negative harness does not change that baseline. Candidate findings remain
candidates, risk remains draft, and final severity or scoring remains manual.

## Malformed input categories

The negative harness fixes these placeholder categories before runtime parser
work starts:

- malformed JSON.
- missing JSON-RPC version.
- invalid method shape.
- oversized message placeholder.
- unexpected batch placeholder.
- tool-call-like payload.
- local-path-like payload.
- raw-request-like payload.
- credential-like payload.

These categories are test planning inputs only. They do not parse, dispatch,
store, echo, or execute any payload body.

## Echo-forbidden contract

Protocol failure handling must not echo:

- request body.
- credential value.
- session value.
- token value.
- local path.
- stack trace.
- actual target identifier.
- raw request or response.
- HMAC secret.
- CSRF token.

The harness treats echo as a failure condition. Later implementation PRs must
return normalized raw-free metadata rather than reflected input.

## Forbidden source markers

The source-check categories are:

- protocol parser implementation marker.
- JSON-RPC parser implementation marker.
- request dispatcher marker.
- tool registration marker.
- tool execution marker.
- local evidence reader marker.
- raw preview or raw download marker.
- external handoff marker.

Any later protocol-facing source file must be declared before it can be checked
against these categories.

## Blocked-response requirements

Malformed or forbidden protocol-like input must result in raw-free blocked
metadata only. The blocked response contract is:

- raw-free blocked response only.
- raw data included false.
- no request body echo.
- no credential, session, or token echo.
- no local path echo.
- no stack trace echo.
- no target identifier echo.
- no raw request or response echo.
- no HMAC secret echo.
- no CSRF token echo.
- no tool dispatch.
- no external handoff.

## Source-check requirements

Before protocol runtime is allowed, future protocol-facing files must be
declared in a fixture and covered by source-check tests. A later PR must fail
if a protocol-facing file includes parser, dispatcher, registration, execution,
local evidence reader, raw preview, dashboard state-changing, upload/import,
replay, active scan, automatic handoff, or sensitive echo markers without a
separate reviewed approval.

## Security review requirements

Every later protocol negative test or implementation PR must state:

- Whether parser runtime is included.
- Whether malformed input can be handled without body echo.
- Whether request dispatch remains blocked.
- Whether tool registration or execution remains blocked.
- Whether local evidence reading remains blocked.
- Whether raw preview or download remains blocked.
- Whether any state-changing dashboard or upload action is included.
- How blocked responses remain raw-free.
- How rollback works without moving release tags.

If any answer expands beyond planning, fixture, source-check, or negative-test
metadata, the work must be split into another PR.

## Rollback expectations

Rollback for this planning and test-boundary PR is a documentation, fixture,
and test revert. A later implementation PR must include its own rollback section
and must not depend on moving release tags or changing GitHub Releases.

## Deferred decisions

- Whether JSON-RPC parsing and MCP protocol parsing should remain separate
  implementation PRs.
- Whether schema validation should start as fixture-only before any runtime
  parser is proposed.
- Whether request dispatch must remain blocked until tool registration and
  execution approval packets are reviewed.
- Whether local evidence reader work should wait until a dedicated path
  traversal and raw-free error model is approved.
