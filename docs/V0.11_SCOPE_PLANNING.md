# v0.11 Scope Planning

## Purpose

This document records the first v0.11 scope planning decision after the v0.10
metadata and safety-boundary release line. It is documentation only.

It does not implement source or runtime behavior, listener or transport
startup, an MCP server, a Burp extension, a web UI, replay or active scan, raw
forwarding, tool execution, repository settings, rulesets, GitHub Issues, tags,
or GitHub Releases.

## Current Usage Form

The current safe usage form is local-first:

```text
Burp export or Burp browsing-derived traffic
-> local redaction
-> verify
-> review
-> report
-> four raw-free AI candidate files
-> manual review before AI use
```

The four AI candidate files remain:

- `analysis_packet.json`
- `chatgpt_prompt.md`
- `codex_task_prompt.md`
- `report_draft.md`

These files are candidates, not external sharing approval. Findings remain
candidates, risk remains draft, and final severity or CVSS remains a manual
decision.

## Fast-Track Web GUI And Burp MCP Path

The v0.11 fast-track goal is to make Web, GUI, and Burp MCP paths look
practically reachable without opening raw Burp traffic, tool execution, or
listener/runtime surfaces.

The fast-track path is three parallel tracks:

| Track | Fast deliverable | Boundary |
| --- | --- | --- |
| Track A | Redacted file viewer planning | No server, no raw preview, no raw download |
| Track B | Localhost-only web UI feasibility | No route implementation, no state-changing controls |
| Track C | Burp MCP adapter feasibility and threat model | No direct MCP bridge, no tool execution |

The preferred sequence is:

1. `v0.11.0`: merge this scope planning document.
2. `v0.11.1`: define `docs/REDACTED_VIEWER_DESIGN.md`.
3. `v0.11.2`: consider a static HTML viewer prototype that reads only
   verified, redacted artifacts from the four-file allowlist.
4. `v0.11.3`: define a localhost web UI threat model covering CSRF, path
   traversal, raw-free output, audit logging, and browser behavior.
5. `v0.11.4`: define a Burp MCP adapter feasibility and threat model covering
   PortSwigger MCP, Montoya, gateway-owned adapter contracts, dry-run behavior,
   allowlists, and audit logging.
6. `v0.12+`: consider actual web or MCP integration only after separate
   approval.

The fast path explicitly does not mean fast raw access. It means fast
reviewability for redacted artifacts.

## Web And GUI Support Possibility

v0.11 may consider a more operator-friendly local review experience, but it
must stay raw-free and local-first.

The lowest-risk GUI direction is a redacted file viewer or local dashboard view
that displays only verified metadata, safe file inventory, report readiness,
and prompt readiness. It must not add raw preview, raw download, upload/import
state changes, dashboard POST actions, replay, active scan, or automatic AI
handoff.

For speed, the first GUI-like deliverable should be a static HTML viewer or
local file viewer design. This keeps the first user-facing improvement away
from server routing, CSRF, cookies, uploads, and local network listener
decisions. A static viewer may only consume verified redacted artifacts from the
four-file allowlist and must fail closed when verify status is missing or
failed.

A localhost-only web UI is feasible only after a separate UI security boundary
reviews:

- loopback-only binding
- CSRF and state-changing action rules
- path traversal prevention
- safe file allowlist
- output alias validation
- audit logging
- raw-free response contracts
- browser cache and download behavior

## Burp MCP Integration Possibility

Burp MCP integration should be treated as a high-risk integration path because
MCP can connect AI applications to external systems and MCP tools may be
invoked by models. PortSwigger's MCP Server extension exposes Burp functionality
through an MCP server and includes capabilities that are close to traffic
analysis, request sending, Burp tool interaction, configuration handling, and
client integration.

For this gateway, direct Burp MCP integration is not the recommended first
v0.11 implementation. The safe first step is a feasibility and threat-model
note that keeps Burp-side access upstream and keeps this gateway downstream as
the redaction and verification boundary.

The v0.11 fast path is an adapter contract, not an adapter implementation. The
contract should define read-only, redacted-only, allowlisted, dry-run, and audit
log requirements before any gateway-owned MCP adapter is implemented.

The safe relationship remains:

```text
Burp or Montoya
-> optional manual upstream inspection
-> local gateway
-> redaction and verify
-> safe file inventory
-> manual AI candidate review
```

The unsafe relationship remains blocked:

```text
AI client
-> direct Burp-side raw traffic or actions
-> automatic external handoff
```

Official MCP guidance treats tools as callable model-controlled capabilities
that interact with external systems. Therefore the gateway must treat MCP
adapter work as a permission boundary, not a simple data-format bridge.

## PortSwigger MCP Extension Relationship

The PortSwigger MCP Server extension is an upstream Burp-side integration. This
gateway must not assume that upstream MCP output is raw-free. Any data from
Burp-side MCP workflows must still pass through local redaction and verify
before becoming an AI input candidate.

v0.11 may document compatibility rules, but it must not implement direct MCP
bridging to Burp, automatic request sending, active scan orchestration,
Collaborator usage, configuration mutation, or automatic AI handoff.

The first Burp MCP-related v0.11 output should be a feasibility and adapter
contract note. It should compare:

- PortSwigger MCP as an upstream Burp-side tool
- Montoya as a Burp extension API path
- a gateway-owned adapter as a downstream redacted-only interface

The note must preserve the rule that upstream Burp-side data is not trusted as
raw-free until it passes this gateway's redaction and verify gates.

## Montoya API Extension Possibility

The Montoya API is the Burp extension API path for building Burp extensions. It
can provide access to Burp functionality such as HTTP, proxy, scanner, scope,
logging, and UI APIs, and it also supports AI-related extension features in
Burp environments that provide them.

A Montoya extension path is feasible only as a separately reviewed integration.
It must not be combined with local GUI work, MCP listener work, tool execution,
or local evidence reading in the same PR. The existing Montoya collector history
should be treated as evidence that Burp extension work needs scoped runtime
smoke and raw-free verification before release decisions.

The Montoya path remains a later integration path. v0.11 may document how a
future extension would hand redacted metadata to the gateway, but it must not
add a Burp extension implementation in the same PR as viewer, web UI, MCP
adapter, or listener work.

## MCP Adapter Possibility

A gateway-owned MCP adapter may be feasible later if it stays read-only,
metadata-only, allowlisted, and raw-free. The adapter should expose only safe
gateway metadata such as:

- gateway status
- verified output aliases
- safe file inventory
- report readiness
- prompt readiness
- troubleshooting categories
- release readiness

The adapter must not expose:

- raw traffic
- local-only file bodies
- credential, token, cookie, or session values
- full local paths
- replay or scan actions
- upload or import actions
- dashboard state-changing actions
- automatic AI handoff
- tool execution results

## Security Risks

The main v0.11 risks are:

- confusing a viewer with external sharing approval
- displaying raw traffic or local file bodies
- leaking target identifiers, credentials, tokens, sessions, or full local paths
- allowing a web UI to perform state-changing actions without a separate
  security review
- treating upstream Burp MCP output as already safe
- treating metadata-only MCP registry work as executable tool registration
- combining listener, transport, parser, dispatcher, tool execution, and local
  evidence reader work in one PR
- changing completed v0.10 release artifacts while planning v0.11

## Raw Traffic Handling Principles

v0.11 must preserve these raw traffic rules:

- Raw request and response bodies are not AI candidate outputs.
- Raw traffic must not be shown in a web or GUI view.
- Raw traffic must not be exposed through MCP tools or resources.
- Raw traffic must not be forwarded to external AI clients.
- Raw-derived findings must remain candidate findings until manual review.
- Any Burp-side upstream integration must route relevant evidence through the
  local redaction and verify gate first.

## Fail-Closed Redaction Gate

The redaction gate must fail closed:

- If redaction cannot prove a file is safe, the output is blocked.
- If verify fails, the file is not an AI candidate.
- If a required safe file is missing, the bundle is not complete.
- If forbidden values are detected, the bundle is not ready.
- If an operator cannot distinguish candidate from approved content, the UI or
  report wording must be corrected before release.

## Audit Log Requirements

Future v0.11 operator-facing work should log raw-free audit metadata for:

- selected project alias
- command or route name
- input class, not input body
- output alias
- verify status
- generated safe file names from the four-file allowlist
- blocked reason code
- manual review requirement
- timestamp

Audit logs must not include raw request or response bodies, credential values,
session values, token values, target identifiers, full local paths, stack trace
bodies, local-only filenames, or local evidence bodies.

## Test Requirements

Any v0.11 implementation PR must add tests that match its surface. Required
categories include:

- document hygiene for planning PRs
- raw-free fixture checks for viewer or adapter output
- safe file allowlist checks
- path traversal and output alias validation for file viewing
- fail-closed redaction and verify behavior
- no raw preview or download checks
- no state-changing dashboard control checks unless separately approved
- no listener, transport, dispatcher, or tool execution markers unless that
  surface is the explicitly approved PR scope
- gitleaks directory and git scans
- GitHub release and tag non-mutation checks for post-release planning work

For viewer or web feasibility work, tests must also cover:

- path traversal labels and fixture cases without recording real local paths
- oversized, binary, and malformed redacted artifact labels
- verify-failed input blocked from rendering
- static viewer output limited to redacted artifacts
- CSRF and same-origin requirements before any state-changing localhost route
  exists

For MCP feasibility work, tests must also cover:

- tool invocation remains unimplemented
- adapter responses remain redacted-only
- allowlist drift is blocked
- audit log fields stay raw-free
- dry-run behavior remains the default before implementation approval

## v0.11 Option Evaluation

### Option A: Keep CLI And Add Redacted File Viewer Only

Recommended first candidate.

This path keeps the current local workflow and adds only a safer review surface
for already verified files. It should begin with a design or fixture PR before
implementation.

Security posture:

- lowest runtime expansion
- no Burp integration required
- no MCP listener required
- no tool execution required
- file access boundary still needs strict allowlist and path validation

Fast-track refinement:

- Option A-1: CLI-preserving redacted static HTML or local file viewer
  planning.
- Option A-2: redacted viewer design PR with input/output, safe file allowlist,
  fail-closed behavior, and fixture plan.

### Option B: Localhost-Only Web UI

Viable after Option A design boundaries are clear.

This path can improve operator usability, especially for first-time users, but
it opens browser-facing risks. It should be split into a feasibility/security
PR before any implementation.

Security posture:

- local-only requirement must be explicit
- state-changing controls require separate CSRF and audit review
- raw preview and raw download remain blocked
- browser cache and download behavior must be reviewed

Fast-track refinement:

- Option B-0: localhost-only web UI feasibility and threat model only.
- Implementation waits until path traversal, CSRF, raw-free output, browser
  cache, and audit boundaries are documented and tested.

### Option C: Burp MCP Adapter Feasibility Only

Viable as a planning PR, not an implementation PR.

This path documents how this gateway should relate to Burp-side MCP tools while
keeping the gateway as the redaction and verification boundary.

Security posture:

- no direct bridge to Burp-side MCP in the first PR
- no AI access to raw Burp traffic
- no request sending, active scan, or replay
- no automatic external handoff

Fast-track refinement:

- Option C-0: Burp MCP adapter feasibility, threat model, and adapter contract
  only.
- Direct integration, listener startup, tool invocation, and raw forwarding
  remain deferred.

### Option D: Direct Burp MCP Integration Implementation

Deferred.

This path is too broad for the first v0.11 slice because it can combine Burp
traffic access, MCP tool invocation, request sending, tool execution semantics,
and external AI client behavior.

### Option E: Listener Or Transport Runtime Implementation

Deferred.

Listener and transport runtime work should not be the first v0.11 user-form
decision. It should remain behind explicit approval packets, source-check
fixtures, negative tests, and rollback requirements.

## v0.11 Recommended Scope

The recommended v0.11 scope is:

1. Option A-1 first: CLI-preserving redacted static HTML or local file viewer
   planning.
2. Option A-2 second: redacted viewer design PR with safe input/output and
   fixture boundaries.
3. Option B-0 third: localhost-only web UI feasibility, not implementation.
4. Option C-0 fourth: Burp MCP adapter feasibility and threat model, not
   implementation.

The first implementation candidate should be small and local-only:

- no runtime listener
- no external transport
- no MCP server startup
- no Burp extension implementation
- no tool execution
- no local evidence body reader outside the safe file allowlist
- no raw preview or download
- no replay or active scan
- no automatic AI handoff
