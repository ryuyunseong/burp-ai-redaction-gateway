# v0.8 Protocol Handler Design

This document defines the v0.8 MCP protocol handler boundary before any
protocol runtime is implemented. It is a design-only and review-boundary
document. It does not add an MCP protocol handler, JSON-RPC parser, protocol
message parser, schema validation runtime, request dispatcher, executable tool
registration, actual tool execution, transport runtime, socket behavior, local
evidence reading, raw preview, dashboard state-changing control, upload or
import behavior, replay, active scan, automatic ChatGPT handoff, tag changes,
or GitHub Release changes.

## Purpose

- Consume the v0.8 backlog split and v0.8 transport design before protocol
  handling is considered.
- Define protocol acceptance, blocked-response, negative-test, and source-check
  expectations before runtime code is added.
- Keep protocol handling separate from transport runtime, tool registration,
  tool execution, local evidence reading, raw preview, and state-changing
  dashboard behavior.
- Preserve the four-file AI input candidate boundary.

## Current v0.8 baseline

The current baseline is the published v0.7 release plus v0.8 backlog split and
transport design-only boundary. The gateway can process local Burp export or
collector output through redaction, verify, review, and report flows, then
present only the existing safe output bundle for human review.

This protocol handler design does not change that baseline. Candidate findings
remain candidates, risk remains draft, and final severity or scoring remains
manual.

## Protocol design scope

This PR may define:

- Protocol handler acceptance criteria.
- Malformed input failure and blocked-response expectations.
- Source-check requirements for future protocol-facing files.
- Negative test categories for forbidden parser, dispatcher, and execution
  behavior.
- Review rules for later protocol implementation PRs.

This PR may not add protocol runtime code.

## Explicit non-goals

This design does not implement or approve:

- Protocol message parser.
- Schema validation runtime.
- Request dispatcher.
- Executable tool registration.
- Actual tool execution.

## Allowed future protocol boundary

A later protocol implementation PR may be considered only after this design is
reviewed and a negative-test harness exists. That later PR must stay separate
from transport runtime, executable tool registration, actual tool execution,
local evidence reading, raw preview, dashboard state-changing control, upload
or import behavior, replay, active scan, and automatic handoff.

Allowed future protocol behavior is limited to a narrow parser boundary that
can classify malformed input and return raw-free blocked or failure metadata.
Any request dispatch, tool call execution, safe file body read, payload body
echo, or external handoff remains outside the protocol PR.

## Forbidden protocol behaviors

The protocol design keeps the following behaviors blocked:

- Parsing MCP protocol messages at runtime.
- Parsing JSON-RPC requests at runtime.
- Running schema validation as a protocol runtime.
- Dispatching requests to tools or local data readers.
- Registering executable tools.
- Dispatching or executing tools.
- Starting transport runtime.
- Opening sockets or accepting connections.
- Starting stdio or HTTP transport runtime.
- Reading local evidence or safe file bodies.
- Previewing or downloading raw data.
- Starting or stopping dashboard services.
- Uploading, importing, replaying, or actively scanning traffic.
- Sending output automatically to ChatGPT or other external systems.
- Echoing request bodies, credential values, session values, token values,
  local paths, stack traces, or target identifiers.
- Claiming final vulnerability, severity, or scoring decisions.

## Failure and blocked-response contract

Malformed protocol input must resolve to a raw-free blocked or failure response
only. A later implementation must not echo the request body, credential values,
session values, token values, local paths, stack traces, actual target
identifiers, or parser internals.

Failure metadata may include only safe status, a normalized reason code, a
manual review requirement, and a raw-data-included false marker. It must not
dispatch tools, read local evidence, start transport runtime, or perform
external handoff.

The blocked response contract is:

- no request body echo.
- no credential, session, or token echo.
- no local path echo.
- no stack trace echo.
- no target identifier echo.
- no tool dispatch.
- no external handoff.

## Required negative tests

Any later implementation PR must include negative tests or source checks that
fail if the PR adds:

- MCP protocol handler runtime before approval.
- JSON-RPC parser runtime before approval.
- Protocol message parser runtime before approval.
- Schema validation runtime before approval.
- Request dispatcher markers.
- Tool registration or execution markers.
- Transport runtime markers.
- Socket bind, listen, or accept markers.
- Stdio or HTTP runtime startup.
- Local evidence reader or file body reader markers.
- Raw preview or raw download markers.
- Dashboard state-changing action markers.
- Upload, import, replay, active scan, or automatic handoff markers.
- Request body echo, credential echo, session echo, token echo, local path
  echo, stack trace echo, or target identifier echo.

Blocked and failure responses must remain raw-free and must not echo sensitive
input values.

## Source-check requirements

Before protocol runtime is allowed, the protocol-facing file list must be
declared in a fixture and covered by source-check tests. A future PR must fail
if a protocol-facing file contains forbidden markers for transport runtime,
request dispatch, tool registration, tool execution, local evidence reading,
raw preview, dashboard state-changing controls, upload or import actions,
replay, active scan, automatic handoff, or sensitive input echo.

## Security review requirements

Every later protocol PR must state:

- Whether any runtime parser is added.
- Whether malformed input is classified without body echo.
- Whether schema validation is runtime code or fixture-only.
- Whether any request dispatcher is included.
- Whether any tool registration or execution is included.
- Whether any local file or evidence reading is included.
- Whether any transport runtime is included.
- Whether any state-changing API is included.
- How blocked responses remain raw-free.
- How rollback works without moving release tags.

If any answer expands beyond protocol metadata classification and raw-free
blocked responses, the work must be split into another PR.

## Rollback expectations

Rollback for this design-only PR is a documentation and fixture revert. A later
protocol implementation PR must include its own rollback section and must not
depend on moving release tags or changing GitHub Releases.

## Deferred decisions

- Whether protocol handler planning should wait for a dedicated negative-test
  harness PR.
- Whether JSON-RPC parsing and MCP protocol parsing should stay in separate
  PRs.
- Whether schema validation should be fixture-only before any runtime parser is
  proposed.
- Whether request dispatch must remain blocked until tool registration and
  execution approval packets are reviewed.
