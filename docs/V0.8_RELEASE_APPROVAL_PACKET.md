# v0.8 Release Approval Packet

This document is a release approval packet only. It organizes the evidence and
checks needed before a later v0.8 tag or GitHub Release action. It does not
create a tag, does not create a GitHub Release, does not move an existing tag,
and does not approve release execution by itself.

## Purpose

- Collect the v0.8 release decision inputs in one reviewable document.
- Keep release approval separate from release execution.
- Tie the PR #130, PR #131, and PR #132 baselines to the final human approval
  step.
- Preserve the local-first, raw-free, four-file AI input candidate boundary.
- Keep v0.8 positioned as a boundary/helper release, not as a read-only MCP
  runtime release.

## Target commit

The approval packet target commit is:

`58c7190e5cde43ca2ae4bddf056360eda649622b`

This target is the current main HEAD at the time this approval packet is
prepared. After this packet is merged, main HEAD must be checked again. A later
release target must be either this approval packet merge commit or a later
explicitly named main HEAD.

## Release type

The proposed release type is `boundary_helper`.

This packet does not describe v0.8 as a read-only MCP runtime release. Listener
startup, transport, protocol parsing, request dispatch, tool registration, tool
execution, and local evidence reading remain deferred.

## Included scope

- redaction, verify, review, and report pipeline
- four AI input candidate files
- dashboard read-only and raw-free baseline
- disabled-by-default MCP helper files
- post-merge boundary note
- scope freeze / RC readiness evidence

## Excluded scope

- listener startup
- socket, bind, listen, or accept behavior
- stdio runtime
- HTTP runtime
- protocol parser
- JSON-RPC parser
- request dispatcher
- executable tool registration
- tool registry runtime
- tool discovery runtime
- actual tool execution
- local evidence reader
- safe file body reader
- raw preview or download
- replay or active scan
- dashboard state-changing control
- upload or import action
- automatic ChatGPT handoff

## Release blockers

The v0.8 release action must stay blocked if any of these are true:

- unit tests fail
- gitleaks directory scan reports a finding
- gitleaks git scan reports a finding
- git safety check fails
- working tree is dirty
- v0.8 tag already exists unexpectedly
- GitHub Release v0.8 already exists unexpectedly
- document or fixture hygiene finds a raw marker or credential marker
- output bundle structure changes
- unreviewed runtime surface is present
- release body describes v0.8 as a read-only MCP runtime release

## Required final gate

Before a later release approval can execute, rerun at least:

- Python compile check
- Python unit test discovery
- gitleaks directory scan
- gitleaks git scan
- git safety check
- diff whitespace check
- clean working tree check
- v0.8 tag absence check
- GitHub Release v0.8 absence check
- release body hygiene check
- tag target verification
- release target verification

These are approval inputs only. They do not create, move, or publish a tag or
release.

## Proposed release note body

The later v0.8 release body should include these sections:

- `Summary`
- `Included boundary/helper scope`
- `Not included`
- `Safety and privacy boundaries`
- `Verification evidence`
- `Manual review requirements`
- `Known limitations`
- `Rollback notes`

The release body must clearly state:

- v0.8 is a boundary/helper release.
- v0.8 is not a read-only MCP runtime release.
- Runtime, parser, dispatcher, tool execution, and local evidence reader
  surfaces are deferred.
- Candidate findings remain candidates.
- Risk remains draft.
- Final severity or scoring remains a manual decision.
- AI input candidates remain limited to the four-file output bundle.

## Required release body hygiene

The release body must preserve these rules:

- No raw request or response content.
- No actual target identifiers.
- No credential values.
- No HMAC key material.
- No CSRF credential value.
- No full local paths.
- No safety guarantee language.
- No verified vulnerability claim.
- No fixed CVSS claim.
- Candidate findings only.
- Draft risk only.
- Manual review required.
- No automatic ChatGPT handoff claim.

## Required tag checks

Before a later release action:

- Confirm the v0.8 tag does not already exist.
- Confirm the selected main commit matches the approved target commit rule.
- Confirm the tag command will point to the selected commit.
- Confirm no tag is created until separate explicit human approval is given.

## Required GitHub Release checks

Before a later GitHub Release action:

- Confirm GitHub Release v0.8 does not already exist.
- Confirm the release target matches the selected v0.8 tag.
- Confirm the release body passes the required hygiene checks.
- Confirm no GitHub Release is created until separate explicit human approval is
  given.

## Rollback requirements

- Before a tag exists, rollback means reverting the approval packet PR and
  rechecking main HEAD.
- After a tag or GitHub Release exists, rollback requires a separate explicit
  rollback plan.
- Do not move tags as part of this packet.
- Do not mutate GitHub Releases as part of this packet.

## Human approval boundary

This packet can support a later release approval discussion, but it is not the
approval itself. A human must explicitly approve the v0.8 target commit, tag
creation, and GitHub Release action after this packet is merged and main HEAD is
rechecked.
