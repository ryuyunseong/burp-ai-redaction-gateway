# v0.7 MCP Listener Skeleton Plan

This document fixes the planning boundary for a future v0.7 MCP listener
skeleton slice. It is a planning, fixture, source-check, and metadata-only
module boundary. It does not implement a listener runtime, transport, protocol
handler, executable tool registration, actual tool execution, local evidence
reader, raw preview, replay, active scan, automatic ChatGPT handoff, tag, or
GitHub Release.

## Purpose

- Consume the v0.7 scope plan before any listener-facing implementation starts.
- Define the source-check scope that must include any listener-facing file
  before it can land.
- Keep the first listener-facing module metadata-only.
- Keep listener skeleton work separate from transport, protocol handling,
  executable registration, execution, and local evidence reading.
- Keep v0.6 release state and the four-file AI input candidate bundle
  unchanged.

## v0.7 Scope Baseline

The v0.7 scope baseline is tracked in
[`V0.7_SCOPE_PLAN.md`](V0.7_SCOPE_PLAN.md). That plan keeps MCP listener work,
UX-only work, and local evidence reader design separated.

This listener skeleton plan consumes that baseline and narrows the MCP listener
path to source-check scope, forbidden source markers, metadata-only helper
behavior, and acceptance criteria. It is not listener runtime implementation
approval. It is not implementation approval for transport, protocol handling,
tool registration, tool execution, or local evidence reading.

The next decision and preflight guard is tracked in
[`V0.7_LISTENER_RUNTIME_DECISION_PREFLIGHT.md`](V0.7_LISTENER_RUNTIME_DECISION_PREFLIGHT.md).
That document must remain planning-only and must not be treated as listener

The later minimal listener runtime approval packet is tracked in
[`V0.7_MINIMAL_LISTENER_RUNTIME_APPROVAL_PACKET.md`](V0.7_MINIMAL_LISTENER_RUNTIME_APPROVAL_PACKET.md).
It is approval evidence only and does not implement listener runtime behavior.

## Listener Skeleton Goal

The listener skeleton goal is to prepare for a later, separately approved
runtime implementation by adding a minimal metadata-only helper module first.
This slice may describe:

- Expected file declaration rules.
- Blocked runtime markers.
- Fixture requirements.
- Acceptance criteria.
- Required tests.
- PR split rules.
- Metadata-only boundary responses.

It must not add runtime files, bind sockets, choose transport, parse protocol
messages, register executable tools, execute tools, read evidence, read file
bodies, create dashboard state changes, or initiate external handoff.

## Acceptance Criteria

This planning slice is acceptable only if:

- `V0.7_SCOPE_PLAN.md` is consumed.
- The listener skeleton plan fixture exists.
- `planning_only` is true.
- Runtime implementation flags are false.
- `metadata_only_skeleton_module_declared` is true.
- v0.6 tag and GitHub Release modification flags are false.
- Output bundle structure change flag is false.
- Source-check scope is declared.
- Future listener files must be declared.
- Existing pre-runtime helper files exist.
- Existing pre-runtime helper files do not contain forbidden source markers.
- The declared metadata-only listener skeleton module exists.
- The metadata helper returns only boundary metadata and blocked responses.
- The document and fixture stay raw-free.

## PR Split Requirements

The following must stay in separate PRs:

- Listener skeleton implementation.
- Transport or protocol handler.
- Executable tool registration.
- Actual tool execution.
- Local evidence reader.
- Raw preview or raw download.
- Dashboard state-changing action.
- Upload or import action.
- Automatic ChatGPT handoff.

Any future PR must state whether it changes runtime behavior, input handling,
output bundle structure, audit behavior, or release state.

## Security Review Checklist

Before any implementation PR, review:

- Whether a listener-facing file is added.
- Whether source-check scope is updated in the same PR.
- Whether socket, transport, or protocol behavior is introduced.
- Whether executable registration or execution is introduced.
- Whether local evidence or file body reading is introduced.
- Whether dashboard or upload state changes are introduced.
- Whether raw data handling changes.
- Whether the four-file AI input candidate bundle changes.
- Whether v0.6 release state changes.

If any runtime or data-handling boundary changes, split the work into a
dedicated security review PR.
