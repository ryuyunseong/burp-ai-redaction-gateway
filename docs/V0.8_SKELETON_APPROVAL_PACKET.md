# v0.8 Skeleton Approval Packet

This document defines the approval packet required before any v0.8 minimal
skeleton runtime PR is proposed. It is an approval-planning and
review-boundary document only. It does not add skeleton runtime, socket
runtime, stdio runtime, HTTP runtime, protocol parsing, JSON-RPC parsing,
request dispatch, tool registration runtime, tool discovery runtime, actual
tool execution, local evidence reading, safe file body reading, raw preview,
dashboard state-changing control, upload or import behavior, replay, active
scan, automatic ChatGPT handoff, tag changes, or GitHub Release changes.

## Purpose

- Require explicit human approval before any runtime PR.
- Fix the disabled-by-default, loopback-only-if-approved, raw-free, and
  manual-review-required conditions for a later minimal skeleton.
- Keep transport, protocol parsing, request dispatch, tool registration, tool
  execution, and local evidence reading as separate approval surfaces.
- Preserve rollback expectations without moving release tags or changing
  GitHub Releases.

## Current v0.8 baseline

The current baseline includes the published v0.7 release, v0.8 backlog split,
v0.8 transport design-only boundary, v0.8 protocol handler design-only
boundary, v0.8 protocol negative test harness, v0.8 tool registration
design-only boundary, v0.8 read-only tool contract, and v0.8 minimal skeleton
planning boundary.

This approval packet does not change that baseline. Candidate findings remain
candidates, risk remains draft, and final severity or scoring remains manual.

## Required approval inputs

A later minimal skeleton runtime PR must provide all of the following before it
can be reviewed:

- Explicit human approval before the runtime PR.
- Target branch and expected base commit named in the PR.
- Implementation scope limited to disabled-by-default behavior.
- Loopback-only condition stated if runtime is later approved.
- Source-check consumption listed.
- Rollback command or plan documented.
- Release tag movement prohibited.
- GitHub Release mutation prohibited.
- Raw-free blocked or disabled response contract listed.
- Manual review and the four-file safe candidate boundary unchanged.

## Pre-implementation blockers

A later runtime PR must stop before implementation when any of these blockers
are present:

- Missing explicit human approval.
- Dirty git status.
- Base branch is not main.
- Unexpected base commit.
- Missing source-check consumption guard.
- Missing raw-free response contract.
- Missing rollback plan.
- Scope contains a protocol parser.
- Scope contains a request dispatcher.
- Scope contains tool execution.
- Scope contains a local evidence reader.
- Scope contains raw preview or raw download.
- Scope contains external handoff.
- Scope contains tag or release mutation.

## Disabled-by-default approval conditions

A later minimal skeleton proposal must show:

- The skeleton remains disabled by default.
- Runtime stays loopback-only if runtime is later approved.
- Protocol parsing remains out of the same PR.
- Request dispatch remains out of the same PR.
- Tool execution remains out of the same PR.
- Local evidence reading remains out of the same PR.
- Safe file body reading remains out of the same PR.
- Blocked or disabled responses remain raw-free.
- Manual review remains required.
- The four-file safe candidate boundary remains unchanged.

## Runtime boundary constraints

The later minimal skeleton PR must not combine skeleton runtime with:

- Protocol parser.
- JSON-RPC parser.
- Request dispatcher.
- Executable tool registration.
- Tool registry runtime.
- Tool discovery runtime.
- Actual tool execution.
- Local evidence reader.
- Safe file body reader.
- Raw preview or raw download.
- Dashboard start or stop control.
- Upload or import action.
- Replay or active scan.
- Automatic ChatGPT handoff.

## Raw-free response requirements

Any future blocked or disabled skeleton response must keep responses raw-free.
The approval packet requires:

- no raw request or response.
- no credential value.
- no session value.
- no token value.
- no HMAC secret.
- no CSRF token value.
- no full local path.
- no actual target identifier.
- no stack trace.
- no file body.
- no external handoff.
- candidate findings only.
- risk draft only.
- final severity is manual.
- final scoring is manual.

## Rollback requirements

A later runtime PR must document rollback before implementation is reviewed.
Rollback must include:

- Revert the runtime PR without moving release tags.
- Revert the runtime PR without changing GitHub Releases.
- Keep output bundle structure unchanged during rollback.
- Keep manual review and four-file safe candidate boundary unchanged.
- Keep blocked or disabled responses raw-free after rollback.

## Required negative tests

A later runtime PR must include negative tests or source checks that fail if
the PR adds:

- Skeleton runtime markers without explicit approval.
- Socket bind, listen, or accept markers without explicit approval.
- Stdio or HTTP runtime markers without explicit approval.
- Protocol parser markers.
- JSON-RPC parser markers.
- Request dispatcher markers.
- Tool registration runtime markers.
- Tool execution markers.
- Local evidence reader markers.
- Safe file body reader markers.
- Raw preview or raw download markers.
- Replay or active scan markers.
- Automatic handoff markers.
- Dashboard state-changing markers.
- Upload or import markers.
- Tag or release mutation markers.

## Source-check requirements

Before any minimal skeleton runtime PR is reviewed, runtime-facing files must
be declared in a fixture and covered by source-check tests. A future PR must
fail if those files contain forbidden markers for socket runtime, stdio
runtime, HTTP runtime, protocol parsing, JSON-RPC parsing, request dispatch,
executable tool registration, tool discovery runtime, tool execution, local
evidence reading, safe file body reading, raw preview, replay, active scan,
automatic handoff, dashboard state-changing control, upload/import behavior,
tag action, or release action without a separate reviewed approval.

The follow-up guard for consuming this approval packet is tracked in
[`V0.8_RUNTIME_SOURCE_CHECK_CONSUMPTION_GUARD.md`](V0.8_RUNTIME_SOURCE_CHECK_CONSUMPTION_GUARD.md).
It declares expected runtime-facing files as fixture metadata only and does not
create those files.

## Security review requirements

Every later skeleton PR must state:

- Who approved the runtime PR.
- Which target branch and expected base commit were reviewed.
- Whether any runtime surface is implemented.
- Whether the skeleton is disabled by default.
- Whether any approved runtime is loopback-only.
- Whether protocol parsing is included.
- Whether request dispatch is included.
- Whether executable registration or tool discovery runtime is included.
- Whether actual tool execution is included.
- Whether local evidence or safe file body reading is included.
- Whether raw preview or download is included.
- Whether replay, active scan, or external handoff is included.
- Whether dashboard state-changing control or upload/import behavior is
  included.
- How blocked and disabled responses remain raw-free.
- How rollback works without moving release tags or changing GitHub Releases.

If any answer expands beyond a disabled-by-default minimal skeleton proposal,
the work must be split into another PR.

## Deferred decisions

- Whether runtime-facing source-check consumption guard should be completed
  before any runtime-facing file is added.
- Whether transport and protocol skeletons should remain separate PRs.
- Whether local evidence reading should wait until a dedicated path traversal
  and raw-free error model is approved.
- Whether tool execution should remain blocked until after transport,
  protocol, registration, and dispatcher behavior are each reviewed.
