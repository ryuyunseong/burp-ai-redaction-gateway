# v0.10 Transport/Listener Approval Packet

## Purpose

This approval packet fixes the transport/listener review boundary before any
listener startup or transport runtime is implemented. It consumes the v0.10
scope decision and keeps listener, transport, protocol handling, executable
tool registration, tool execution, local evidence reading, raw preview, replay,
dashboard state-changing action, upload/import action, and automatic handoff
out of this PR.

## Approval scope

This PR approves only a planning packet. It defines the minimum review inputs
for a future transport/listener implementation PR and does not approve runtime
startup, network binding, protocol handling, tool registration, tool execution,
local file access, raw preview, replay, dashboard state changes, upload/import,
or automatic handoff.

This PR does not allow or implement:

- listener implementation
- transport runtime

- server startup
- protocol handler
- executable tool registration
- actual tool execution
- local evidence reader
- safe file body reader
- raw preview/download

## Transport choices

MCP transport planning is JSON-RPC based. The planning values allowed by this
packet are `stdio_planning`, `streamable_http_planning`, and
`custom_transport_deferred`.

`stdio_planning` and `streamable_http_planning` are labels only. Streamable HTTP
runtime is not implemented by this PR. Custom transport remains deferred until
a separate approval packet defines its trust boundary.

## Listener startup boundary

Listener startup is blocked in this PR. A future implementation PR must first
show how startup is disabled or explicitly gated, how startup failure is
reported as raw-free metadata, and how startup avoids tool execution, local
evidence access, raw preview, replay, and automatic handoff.

## Localhost binding boundary

Loopback-only binding is required before any listener runtime is considered.
This packet does not implement binding and does not introduce socket startup.
A future implementation PR must reject any non-local bind plan before runtime
is enabled.

## Origin validation boundary

Origin validation is required before Streamable HTTP runtime is considered.
This packet does not implement HTTP transport and does not parse runtime
headers. A future implementation PR must define fail-closed handling for
missing, unsupported, or untrusted origin metadata before runtime is enabled.

## Authentication and authorization boundary

Remote transport requires a separate authentication and authorization boundary
before implementation. This packet does not add authentication, authorization,
session validation, credential forwarding, or delegated access.

Token passthrough is forbidden. A future implementation must not forward
caller-provided credential values to downstream tools or services as an
authorization substitute.

## Session handling boundary

Stateful transport requires a separate session policy before implementation.
The future policy must define session identifier generation, storage, expiry,
and invalidation boundaries without logging or echoing credential values,
target identifiers, local paths, raw traffic, or evidence body content.

## Blocked response boundary

Blocked transport/listener responses must be raw-free metadata only. Allowed
blocked response fields are limited to status, reason_code,
approval_packet_only, raw_data_included, manual_review_required, and
safe_message.

Blocked responses must not echo raw input, credential values, target
identifiers, local paths, stack traces, tool execution results, or local
evidence body content.

## Audit and logging boundary

Future audit records must remain raw-free. They may record synthetic reason
codes, planning labels, false runtime flags, and manual-review requirements.
They must not record raw request or response bodies, credential values, target
identifiers, local paths, stack traces, local evidence bodies, or tool execution
results.

## Source-check requirements

This approval packet is document, fixture, README link, and hygiene test only.
Runtime source files must not be modified by this PR. Future implementation PRs
must include source checks for network startup, protocol handling, execution,
file body reading, raw preview, replay, and automatic handoff markers.

## Required negative tests

Future transport/listener work must include negative tests for:

- rejecting non-local bind plans;
- rejecting Streamable HTTP plans without origin validation;
- rejecting remote transport plans without authentication boundary;
- rejecting token passthrough plans;
- rejecting listener plus tool execution combinations;
- rejecting listener plus local evidence reader combinations;
- rejecting transport plus raw preview combinations;
- keeping socket startup absent until implementation approval;
- keeping runtime code unchanged in approval-only PRs;
- keeping audit output raw-free.

The v0.10 listener startup negative fixture harness is tracked in
`tests/fixtures/v10_listener_startup_negative_cases.json`. This harness is not
a runtime implementation. It does not add socket bind, listen, or accept
behavior. It does not add a protocol handler, tool execution, local evidence
reading, raw preview, replay, state-changing actions, upload/import, or
automatic handoff. A future listener implementation PR must consume this
fixture before opening any startup surface.

The v0.10 listener startup implementation decision is tracked in
`docs/V0.10_LISTENER_STARTUP_IMPLEMENTATION_DECISION.md` and
`tests/fixtures/v10_listener_startup_implementation_decision.json`. It allows
only a future listener startup skeleton step. It does not approve listener
runtime, transport runtime, socket startup, protocol handling, tool execution,
local evidence reading, raw preview, replay, state-changing actions,
upload/import, or automatic handoff.

The v0.10 listener startup skeleton is tracked in
`burp_ai_redaction_gateway/mcp_listener_startup_skeleton.py` and
`tests/fixtures/v10_listener_startup_skeleton.json`. It is disabled-by-default
metadata only and keeps listener runtime, transport runtime, socket startup,
protocol handling, executable registration, actual tool execution, local
evidence reading, raw preview/download, replay, state-changing actions,
upload/import, and automatic handoff outside this packet.

## PR split requirements

The following combined PRs are blocked:

- listener plus tool execution
- listener plus local evidence reader
- transport plus raw preview
- listener plus server startup
- transport plus protocol handler
- tool execution plus local evidence reader

## Security review checklist

Before any future runtime PR is approved, reviewers must confirm:

- loopback-only binding is enforced;
- non-local bind plans fail closed;
- Streamable HTTP origin validation is defined before runtime;
- remote transport authentication and authorization boundaries are defined;
- token passthrough is forbidden;
- session policy is defined before stateful transport;
- blocked responses are raw-free metadata only;
- audit records do not include raw traffic, credential values, target
  identifiers, local paths, stack traces, local evidence bodies, or tool
  execution results;
- tool execution and local evidence reader remain separate threat-boundary PRs.
