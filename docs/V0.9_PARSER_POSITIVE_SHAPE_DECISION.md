# v0.9 Parser Positive Shape Decision

## Purpose

This decision record fixes the allowed future positive parser output shape
before any positive parser implementation starts. It follows the merged
blocked-only parser baseline and keeps dispatcher, tool execution, listener,
transport, and local evidence reader work outside this slice.

## Current Baseline

- main HEAD: `bc4b950cf20aee24f968e9ff28f037cf1072b741`
- PR #139 merge commit: `bc4b950cf20aee24f968e9ff28f037cf1072b741`
- minimal blocked-only parser: merged
- positive parser shape: not implemented
- dispatcher implementation: not implemented
- listener or transport runtime: not implemented
- tool execution: not implemented
- local evidence reader: not implemented
- v0.9 tag: not created
- GitHub Release v0.9: not created

## Decision Status

This record is planning only. Positive parser implementation still requires a
separate explicit approval. The decision only defines the response shape that a
future positive parser candidate may request approval to implement.

## Allowed Future Positive Shape Candidate

After explicit approval, a future parser PR may propose read-only structured
parse metadata only. The candidate must:

- classify a supported read-only message shape without invoking a dispatcher
- avoid tool lookup and executable tool registration
- avoid actual tool execution
- avoid listener startup or transport runtime changes
- avoid local evidence reader and safe file body reader behavior
- avoid raw input echo
- avoid credential, session, or token echo
- avoid target identifier echo
- avoid URL, domain, IP, or local path echo
- keep negative blocked cases unchanged
- keep `raw_data_included` false
- keep `manual_review_required` true

## Allowed Positive Response Fields

A future positive parser candidate may request approval for only these response
fields:

- `status`
- `reason_code`
- `parser_approved`
- `raw_data_included`
- `manual_review_required`
- `safe_message`
- `message_kind`
- `protocol_version_supported`
- `normalized_method_label`

`normalized_method_label` must be an allowlisted synthetic label. It must not be
derived by echoing an untrusted method string.

## Forbidden Positive Response Fields

A future positive parser response must not include fields that can carry raw
traffic, target identity, credentials, local paths, file bodies, or stack traces.
Forbidden field names include:

- `raw_input`
- `raw_request`
- `raw_response`
- `target`
- `url`
- `domain`
- `ip`
- `credential`
- `token`
- `session`
- `local_path`
- `file_body`
- `stack_trace`

## Required Tests

Before any future positive parser implementation can merge, tests must prove:

- positive shape returns allowlisted fields only
- positive shape does not echo raw input
- positive shape does not echo credential, session, or token values
- positive shape does not echo target identifiers
- positive shape does not echo URL, domain, IP, or local path values
- positive shape has no dispatcher side effect
- positive shape has no tool lookup, registration, or execution side effect
- positive shape has no local evidence reader or file body side effect
- blocked negative fixture cases remain unchanged
- raw-free and manual-review-required flags remain enforced

## Forbidden Scope

This decision does not approve:

- positive parser implementation
- JSON-RPC parser implementation
- dispatcher implementation
- listener startup
- transport runtime
- executable tool registration
- actual tool execution
- local evidence reader
- safe file body reader
- raw preview or download
- replay or active scan
- dashboard state-changing control
- upload or import action
- automatic ChatGPT handoff
- v0.9 tag creation
- GitHub Release v0.9 creation

## Source-check Requirements

Future implementation PRs must keep source checks active for parser files and
must fail if a positive parser slice adds dispatcher, tool execution, local
evidence reader, listener, transport, raw preview, replay, upload, or handoff
markers.

## Rollback Requirements

If a future positive parser implementation expands into dispatcher, tool
execution, listener, transport, or local evidence reader behavior, split or
revert that implementation. This decision record and fixture may remain as the
planning baseline unless their boundaries are found to be incorrect.
