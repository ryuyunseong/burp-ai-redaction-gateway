# v0.10 Tag and Release Protection Review

## Purpose

v0.10 is complete. This note records the current release state and reviews
policy options for reducing accidental or unauthorized tag and GitHub Release
mutation risk before v0.11 planning continues.

This is a policy review draft only. It does not change repository settings,
rulesets, tags, GitHub Releases, source code, runtime behavior, tests, or
release notes.

## Risk Summary

Without a visible active tag or release immutability policy, v0.10 preservation
currently depends on manual process and explicit verification. The main risks
are:

- a release tag could be moved or deleted by someone with sufficient
  permissions;
- a release could be edited in a way that makes the release record drift from
  the post-release evidence;
- future work could confuse `main` movement with the immutable release target;
- later v0.11 work could accidentally touch v0.10 release records.

These risks are policy and governance risks. They do not indicate a runtime,
redaction, parser, dashboard, MCP, or data handling defect.

## Option A: Keep Manual Verification Only

Keep the current state and continue verifying tag and release state manually
before release-adjacent work.

Pros:

- No repository settings mutation.
- Lowest operational risk for this turn.
- Keeps v0.10 release unchanged.

Cons:

- Relies on humans to remember the check.
- Does not prevent tag or release mutation by itself.
- Does not protect future `v*` tags automatically.

Status: active current behavior.

## Option B: Add a Tag Ruleset for Release Tags

Create a repository ruleset targeting release tags, such as `v*`, in a separate
approved settings task.

Expected intent:

- restrict release tag deletion;
- restrict release tag updates or force movement;
- restrict release tag creation to intended release operators;
- keep the ruleset active or explicitly disabled during a staged rollout,
  depending on reviewer approval.

Pros:

- GitHub rulesets can target tags and control how users interact with selected
  tags.
- A `v*` tag pattern would protect future release tags, not only v0.10.
- Ruleset state remains visible to repository readers.

Cons:

- Requires repository settings mutation.
- Requires careful bypass and admin policy review.
- A broad `v*` pattern can affect all future release workflows.

Status: recommended first protection option, but not applied by this review.

## Option C: Evaluate Immutable Releases

Evaluate GitHub immutable releases for future releases in a separate approved
settings task.

Expected intent:

- future immutable releases lock the associated tag to its commit while the
  release exists;
- future release assets are protected from modification or deletion after
  publication;
- the workflow should publish with all intended assets already attached.

Important limitation:

- GitHub documentation states that enabling release immutability applies only to
  future releases. This review does not claim that existing v0.10 release state
  becomes immutable retroactively.

Status: useful future-release option, but applicability must be checked before
use.

## Option D: Defer Tag Ruleset and Immutable Releases

Defer both tag ruleset and immutable release policy until v0.11.

Pros:

- No repository settings mutation now.
- Avoids blocking immediate v0.11 planning.

Cons:

- Leaves release integrity dependent on manual checks.
- Allows the same risk to persist into v0.11 release preparation.

Status: acceptable only if the project explicitly accepts manual verification
as the short-term control.

## Recommendation

Recommended path: keep v0.10 unchanged, then evaluate Option B as the first
separate settings-level task. A tag ruleset for `v*` is the most direct
candidate because it protects the release-tag boundary without changing the
already published v0.10 release record.

Option C should be reviewed for future releases, but it should not be described
as retroactive protection for v0.10 unless GitHub state proves that behavior.

Until a separate approval is granted, Option A remains the active control:
manual verification of tag target, release state, and ruleset state before
release-adjacent work.

## Precautions Before Applying Any Policy

Before creating a tag ruleset or enabling release immutability, perform a
separate approved settings task that:

- confirms repository admin permission and the exact GitHub plan capability;
- records the current `v0.10` tag target before and after any settings change;
- decides whether the tag pattern should be `v*` or a narrower release pattern;
- reviews bypass actors and admin override behavior;
- confirms release automation, if any, will still be able to create intended
  future release tags;
- keeps v0.10 tag and GitHub Release mutation out of scope;
- records rollback or disable steps for settings-only changes.
