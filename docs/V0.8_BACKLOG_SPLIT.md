# v0.8 Backlog Split

This document splits the v0.8 backlog after the published v0.7 release,
post-release smoke, and one local-only operational smoke. It is a planning and
review-boundary document only. It does not implement transport, protocol
handling, tool registration, tool execution, local evidence reading, raw
preview, dashboard state-changing control, upload or import behavior, replay,
active scan, automatic ChatGPT handoff, tag changes, or GitHub Release changes.

## Purpose

- Preserve the completed v0.7 release baseline before opening new runtime
  surfaces.
- Separate each high-risk MCP, dashboard, upload, raw-data, and handoff surface
  into its own design or approval PR.
- Keep the four-file AI input candidate boundary unchanged.
- Keep candidate findings, draft risk, and manual review language visible for
  every later feature slice.

## Current v0.7 baseline

The current baseline is the published v0.7 release. It includes local
redaction, verify, review, report, release evidence, post-release tag checkout
smoke, and one local-only operational smoke. The baseline keeps output for AI
review limited to the existing four-file candidate bundle.

The baseline does not make findings final, does not make risk scoring final,
does not approve external sharing, and does not add automatic ChatGPT handoff.

High risk:

## Required PR split

The following work must be split into separate PRs:

- Transport design.
- Protocol handler design.
- Tool registration design.
- Tool execution approval packet.
- Local evidence reader threat model.
- Raw preview or download decision.
- Dashboard state-changing control threat model.
- Upload or import action threat model.
- Replay or active scan decision.
- Automatic ChatGPT handoff decision.

No PR should combine transport, protocol handling, tool execution, local
evidence reading, raw preview, replay, active scan, dashboard state-changing
control, upload or import action, and automatic handoff.

## Security review requirements

Every later v0.8 design or implementation PR must state:

- Whether a runtime surface is added.
- Whether input validation changes.
- Whether raw data handling changes.
- Whether credential, session, personal data, or local path handling changes.
- Whether a state-changing route or action is added.
- Whether audit behavior changes.
- Whether the four-file AI input candidate boundary changes.
- How failure responses remain raw-free.
- How rollback works without moving release tags.

If a PR changes any security boundary, it must stay narrow and must not include
unrelated UX, documentation, or release work.

## Testing requirements

Before any implementation PR for a candidate surface, require:

- Source-check coverage for the files that can open the surface.
- Negative tests for forbidden operations.
- Raw-free blocked or error response checks.
- Secret scan and git safety checks.
- A clear statement that candidate findings remain candidates, risk remains
  draft, and final severity or scoring remains manual.

## Recommended order

1. Transport design only.
2. Protocol handler design only.
3. Protocol negative test harness.
4. Transport and protocol minimal skeleton, disabled by default.
5. Dashboard UX and documentation polish.
6. Local evidence reader threat model.
7. Tool execution approval packet.

Actual implementation stays blocked until the relevant design, threat model,
approval packet, and negative tests are reviewed in separate PRs.

The transport design-only follow-up is tracked in
[`V0.8_TRANSPORT_DESIGN.md`](V0.8_TRANSPORT_DESIGN.md). It is a planning
boundary only and does not implement socket, stdio, HTTP, protocol, tool,
evidence-reader, raw preview, dashboard action, upload/import, replay, active
scan, or automatic handoff behavior.

The protocol handler design-only follow-up is tracked in
[`V0.8_PROTOCOL_HANDLER_DESIGN.md`](V0.8_PROTOCOL_HANDLER_DESIGN.md). It is a
planning boundary only and does not implement an MCP protocol handler,
JSON-RPC parser, request dispatcher, tool registration, tool execution,
transport runtime, local evidence reader, raw preview, dashboard action,
upload/import, replay, active scan, or automatic handoff behavior.

## Deferred decisions

- Whether v0.8 should prioritize MCP transport or dashboard UX.
- Whether protocol parsing should stay design-only until another operational
  smoke sample is collected.
- Whether local evidence reading should be postponed until a dedicated path
  traversal and raw-free error model is approved.
- Whether tool execution should remain blocked until after transport and
  protocol behavior are proven disabled by default.
