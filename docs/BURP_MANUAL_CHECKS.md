# Burp에서 검토 후보 확인하기

보고서에 나온 항목을 Burp에서 확인하는 방법입니다. 검토 후보는 확정 취약점이 아닙니다.
`demo`는 가상 기록이며 접속할 서버가 아닙니다. 이 문서는 재현 결과가 아닌 점검 방법입니다.
별도의 허가된 실습 환경과 테스트 자료가 필요합니다. 결과를 만드는 방법은 [사용 방법](USAGE.md)을 참고하세요.

## 시작 전 준비

1. 테스트 계정 A·B로 각각 다른 브라우저 세션에 로그인합니다. 두 계정 모두 자기 자료를 조회할 수 있는지 확인하세요.
2. 일반 조회는 같은 권한의 A·B로 비교합니다. 관리자 조회는 일반 계정 A와 조회 권한이 있는 관리자 B를 사용합니다. 계정 권한을 바꾸지 않습니다.
3. 계정별로 볼 수 있는 자료를 먼저 정합니다. 필요한 계정이나 자료가 없으면 미확인으로 남기세요.
4. Burp의 Proxy → HTTP history에서 조회 요청을 우클릭해 Send to Repeater를 누릅니다. 먼저 요청을 바꾸지 않고 Send를 눌러 원래 응답을 확인하세요.

아래의 `{id}`, `{uuid}`는 값을 가린 표시입니다. 실습에서 알고 있는 테스트 번호만 사용하세요.
로그인 정보와 조회 대상을 동시에 바꾸지 마세요. 요청을 보낼 때 어느 계정의 로그인 정보인지 확인합니다.
쿠키 확인은 로그인 흐름을 관찰하고, 나머지는 허용된 읽기 전용 조회만 사용합니다.
보안 검사·브라우저 보호를 끄거나, 자동 스캔·번호 대입·대량 조회·수정·삭제 요청을 하지 않습니다.

## 가상 샘플의 후보 번호

| 유형 | 후보 번호 |
| --- | --- |
| 접근 권한 2건 | FC-0004, FC-0019 |
| 민감정보 포함 4건 | FC-0005, FC-0008, FC-0015, FC-0020 |
| 쿠키 보호 설정 2건 | FC-0002, FC-0010 |
| 캐시 설정 4건 | FC-0003, FC-0007, FC-0014, FC-0018 |
| CORS 설정 1건 | FC-0012 |
| 오류 메시지 1건 | FC-0016 |
| 보안 헤더 8건 | FC-0001, FC-0006, FC-0009, FC-0011, FC-0013, FC-0017, FC-0021, FC-0022 |

같은 응답에서 여러 후보가 나올 수 있으므로, 22건은 서로 다른 취약점 22개를 뜻하지 않습니다.
번호는 이 가상 샘플 기준입니다. 내 기록에서는 번호 대신 유형과 대상 요청을 확인하세요.

## 1. 접근 권한

1. 프로필 `GET /api/users/{id}/profile`에서 A·B가 각자 자기 자료를 조회한 응답을 확인합니다.
2. A의 로그인 정보는 그대로 두고 번호만 B의 테스트 번호로 바꿉니다. B에서도 번호만 A의 것으로 바꿔 비교하세요.
3. 관리자 조회 `GET /admin/users/{id}`는 B의 정상 요청에서 번호는 그대로 두고 인증용 쿠키·헤더만 A의 것으로 바꿉니다. B의 인증정보가 남지 않았는지 확인하세요.

- 정상: 권한 없는 자료를 거부하거나 비공개 정보를 반환하지 않습니다.
- 문제 의심: 다른 계정의 비공개 자료나 일반 계정이 볼 수 없는 관리자 정보가 나옵니다.

원래 공개되거나 공유가 허용된 자료는 문제로 판단하지 않습니다.

## 2. 민감정보 포함

1. A·B의 정상 응답에서 화면과 응답 본문을 비교합니다. 각 항목이 기능에 필요한 정보인지 확인하세요.
2. 프로필은 1번 ‘접근 권한’ 순서로 확인합니다. 주문 `GET /api/orders/{uuid}`는 A의 로그인 상태에서 번호만 B의 테스트 주문 번호로 바꿉니다.
3. 보고서 `GET /api/reports/export`는 같은 조건으로 조회해 계정별 허용 범위와 비교합니다. 관리자 사용자 조회는 B의 정상 요청에서 로그인 정보만 A로 바꿉니다.

- 정상: 기능과 권한에 필요한 정보만 반환합니다.
- 문제 의심: 다른 계정의 비공개 항목이나 기능에 불필요한 민감정보가 나옵니다.

민감정보가 가려졌다는 표시만으로 유출을 확정하지 않습니다. 화면에 없는 항목도 용도와 권한을 확인하세요.

## 3. 쿠키 보호 설정

가상 샘플의 원본 응답에서 확인한 속성입니다. 쿠키 값은 표시하지 않습니다.

| 후보 / 쿠키 | Secure | HttpOnly | SameSite |
| --- | --- | --- | --- |
| FC-0002 / session | 없음 | 있음 | Lax |
| FC-0010 / sid | 없음 | 없음 | None |

보고서는 `SameSite` 속성 누락과 `SameSite=None`인데 `Secure`가 없는 경우를 구분합니다. `sid`는 속성이 있지만 `Secure`가 없습니다. 이전에 만든 결과는 다시 처리해야 새 기준이 반영됩니다.

1. A로 HTTPS 로그인·프로필 조회를 하고 응답의 `Set-Cookie`를 확인합니다. 로그인 중간의 `302` 응답도 확인하세요.
2. B에서도 반복합니다. 쿠키를 서로 교환하지 말고, 로그인 유지용인지와 발급·갱신 때의 보호 속성을 비교합니다.
3. 브라우저 개발자 도구에서 저장된 속성도 확인합니다. Chrome은 Application → Storage → Cookies에서 읽기만 합니다.

- 정상: 로그인 유지용 쿠키에 `Secure`와 용도에 맞는 `HttpOnly`·`SameSite` 설정이 있습니다.
- 문제 의심: 민감한 로그인 쿠키에 필요한 속성이 없거나, `SameSite=None`인데 `Secure`가 없습니다.

`SameSite` 누락 시 일부 브라우저는 `Lax`를 기본 적용합니다. `None`은 필요한 경우에만 사용하며 `Secure`가 필요합니다.
`Set-Cookie`가 없으면 발급 응답을 아직 못 찾았을 수 있습니다. Repeater 전송 성공만으로 브라우저 보호 동작을 판단하지 않습니다.

## 4. 캐시 설정

프로필·주문·보고서·관리자 사용자 조회가 대상입니다. 가상 샘플에는 `no-store`, `no-cache`, `private`가 없었습니다.

1. A의 비공개 자료를 조회한 뒤 주소·조회 조건은 그대로 두고 로그인 정보만 B로 바꿉니다. 관리자 요청은 반대로 B에서 A로 바꿉니다.
2. 권한 없는 자료가 나오거나 보고서에 이전 계정의 자료가 섞이는지 확인합니다. `Age`, `X-Cache`만으로 캐시 재사용을 확정하지 않습니다.
3. 브라우저 캐시는 같은 테스트 브라우저에서 A 로그아웃 → B 로그인 → 같은 주소 다시 열기 순서로 확인합니다. 캐시를 지우거나 강제로 우회하지 않습니다.

- 정상: 해당 계정이 볼 수 있는 자료만 반환하고, 자료의 민감도에 맞는 캐시 정책을 적용합니다.
- 문제 의심: 이전 계정의 비공개 자료가 재사용됩니다. 캐시 때문인지 접근 권한 누락 때문인지는 별도로 확인하세요.

`no-store`는 저장 금지, `private`는 공유 캐시에 저장 금지, `no-cache`는 재사용 전 서버 확인입니다. 세 가지가 모두 있어야 정상인 것은 아닙니다.
뒤로가기로 보이는 과거 화면만으로 공유 캐시 유출을 확정하지 않습니다.

## 5. CORS: 다른 사이트의 응답 읽기

대상은 `OPTIONS /api/admin/users`입니다. 가상 샘플만으로 로그인 상태에서 다른 사이트가 응답을 읽을 수 있는지는 알 수 없습니다.

1. 사전 확인 요청인 `OPTIONS`와 그 뒤의 실제 읽기 전용 요청을 찾습니다. Repeater에서 `Origin`만 허용된 사이트에서 허용하지 않은 테스트 사이트로 바꿉니다. 대상 주소와 메서드는 유지하세요.
2. 두 응답의 `Access-Control-Allow-Origin`과 `Access-Control-Allow-Credentials`를 확인합니다. `OPTIONS`에 A·B의 인증용 쿠키·헤더를 임의로 붙이지 않습니다.
3. 허가된 다른 출처의 테스트 페이지에서 A·B 각각의 비공개 응답을 스크립트로 읽을 수 있는지 확인합니다. 쿠키 인증은 `credentials: "include"`를 사용하되 기존 쿠키 제한은 유지합니다. 쿠키·토큰을 페이지에 직접 붙여 넣지 마세요.

- 정상: 허용하지 않은 사이트의 스크립트가 비공개 응답을 읽지 못하고, 계정 권한도 그대로 적용됩니다.
- 문제 의심: 그 사이트가 로그인 상태를 이용해 비공개 응답을 읽습니다. Burp에서 응답이 보이는 것만으로는 부족합니다.

인증정보 포함 요청에 `Access-Control-Allow-Origin: *`가 반환되면 브라우저는 읽기를 차단합니다. 공개 자료의 `*`도 그 자체로 취약점은 아닙니다.
테스트 페이지가 없거나 실제 요청에 로그인 정보가 전달되지 않았다면 브라우저 검증은 미확인입니다.

## 6. 오류 메시지

대상은 `GET /api/debug/{id}`입니다. 가상 샘플의 오류 신호만으로 내부 정보 노출을 확정할 수 없습니다.

1. A의 정상 조회에서 번호만 미리 정한 오류 확인용 테스트 번호로 바꿔 한 번 전송합니다.
2. 응답 헤더·본문에 내부 경로, 함수 호출 목록, 데이터베이스 쿼리, 비밀정보가 보이는지 확인합니다.
3. B에서도 같은 조건으로 비교합니다. 디버그 모드를 켜거나 긴 입력·공격 문자열로 오류를 강제하지 않습니다.

- 정상: 사용자에게 필요한 오류 안내만 보여 주고 내부 진단 정보는 숨깁니다.
- 문제 의심: 권한 없는 사용자에게 내부 정보나 비밀정보가 보입니다.

`500` 응답이나 문의용 추적번호만으로는 정보 노출이 아닙니다. 재현되지 않거나 권한 조건이 불명확하면 미확인입니다.

## 7. 보안 헤더

1. A·B의 정상 응답에서 `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`를 확인합니다.
2. HTML 화면·API·`OPTIONS`별로 필요한 보호가 다를 수 있습니다. 실제 서비스 경로와 앞단 서버가 추가하는 헤더도 확인하세요.

- 정상: 해당 응답에 필요한 보호가 실제 서비스 경로에 적용됩니다.
- 추가 검토: 필요한 보호가 빠져 있습니다. 헤더 누락만으로 공격 성공이나 피해를 단정하지 않습니다.

## 결과를 판단할 때

`200 OK`나 응답 길이만 보지 말고 내용을 확인하세요. `401`·로그인 화면은 세션 만료일 수 있고, 본문 없는 `304`만으로도 판단할 수 없습니다.
계정 역할, 확인한 항목, 응답 코드, 판단과 미확인 사유만 기록하세요. 실제 값·쿠키·토큰·원문은 채팅이나 GitHub에 올리지 마세요.
MCP는 검증된 결과를 읽을 뿐 Burp에서 재전송하거나 직접 재현하지 않습니다. 위 절차는 사람이 별도로 수행합니다.
