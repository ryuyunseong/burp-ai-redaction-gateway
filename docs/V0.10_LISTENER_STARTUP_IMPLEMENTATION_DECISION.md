# v0.10 Listener Startup Implementation Decision

## Purpose

This decision fixes the minimum conditions for the next listener startup
skeleton PR. It consumes the v0.10 transport/listener approval packet and the
listener startup negative fixture harness before any startup surface is opened.

This document does not implement listener runtime. It approves only a future
listener startup skeleton path that remains local-only, blocked-by-default, and
separate from transport runtime, protocol handling, tool registration, tool
execution, local evidence reading, raw preview, replay, dashboard state
changes, upload/import, and automatic handoff.

## Implementation decision scope

The approved next step is `listener_startup_skeleton_only`.

That future PR may define static startup metadata, disabled-by-default startup

## Listener startup preconditions

Before listener startup can move beyond skeleton metadata, all of the following
must remain explicit acceptance criteria:

- loopback-only binding is required;
- non-local binding is rejected before runtime;
- origin validation is required before any HTTP runtime;
- remote transport requires a separate authentication boundary;
- token passthrough is forbidden;
- session policy is required before stateful transport;
- protocol handler remains deferred;
- tool execution remains deferred;
- local evidence reader remains deferred;
- raw preview remains deferred.

## Localhost binding decision

The next PR may describe loopback-only startup configuration but must not bind a
socket or start a server. Any non-local bind plan must remain blocked and must
return raw-free metadata only.

## Origin validation decision

Origin validation is a prerequisite for any HTTP runtime. The next PR must not
implement HTTP transport, parse runtime headers, or accept protocol messages.
If origin validation is missing from a future runtime plan, the plan must fail
closed before startup.

## Authentication boundary decision

Remote transport requires a separate authentication and authorization boundary.
The listener startup skeleton must not introduce authentication, delegated
access, credential forwarding, executable registration, or tool invocation.

## Session policy decision

Stateful transport requires a session policy before runtime. Session identifiers
must not be treated as authentication, must be generated with secure
non-deterministic values, and should bind to user context where applicable.
Session identifiers and credential-derived values must not be logged or echoed.

## Token passthrough decision

Token passthrough remains forbidden. A caller-supplied credential value must not
be forwarded to tools, adapters, local evidence readers, dashboard actions, or
external services as an authorization substitute.

## Blocked response contract

Blocked startup responses must stay raw-free and metadata-only. Allowed fields
must be limited to status, reason_code, startup_skeleton_only,
raw_data_included, manual_review_required, and safe_message unless a later
approval packet narrows or extends the contract.

Blocked responses must not echo input body content, credential values, target
identifiers, local paths, stack traces, tool execution results, or local
evidence body content.

## Runtime separation requirements

The listener startup skeleton must remain separate from:

- transport runtime
- protocol handler
- executable tool registration
- actual tool execution
- local evidence reader
- safe file body reader
- raw preview/download
- replay or active scan
- dashboard state-changing action
- upload/import action
- automatic ChatGPT handoff

Any one of those surfaces requires a separate approval packet or threat-boundary
PR before implementation.
