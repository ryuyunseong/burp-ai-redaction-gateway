# v0.8 Post-Merge Boundary Note

This document fixes the post-merge boundary after PR #130. It records what the
disabled-by-default minimal skeleton helper merge added, what remains outside
the implementation scope, and which follow-up surfaces must stay split into
separate approval PRs.

This note is documentation, fixture, and test evidence only. It does not add
runtime behavior, protocol parsing, request dispatch, tool registration, tool
execution, local evidence reading, raw preview or download, dashboard actions,
upload or import behavior, replay, active scan, automatic ChatGPT handoff, tag
changes, or GitHub Release changes.

## Purpose

- Record PR #130 merge commit `fcc0dd947ec9c62410cc5715cce7ae623bc32aa8` as
  the post-merge baseline for the disabled-by-default minimal skeleton helper.
- Keep the implemented scope limited to two helper modules and raw-free
  disabled or blocked responses.
- Make clear that listener startup, transport, protocol parsing, request
  dispatch, tool registration, tool execution, and evidence reading remain
  separate work.
- Preserve the four-file AI input candidate boundary.
- Keep v0.8 tag and GitHub Release work blocked until explicit approval.

## Current baseline

PR #130 is merged into main at
`fcc0dd947ec9c62410cc5715cce7ae623bc32aa8`.

Implemented scope is limited to:

- `burp_ai_redaction_gateway/mcp_minimal_skeleton.py`
- `burp_ai_redaction_gateway/mcp_runtime_contract.py`
- disabled-by-default metadata helpers
- raw-free disabled response helpers
- loopback candidate validation helper

The helper boundary keeps candidate findings as candidates, risk as draft, and
final severity or scoring as a manual decision.

## Implemented helper boundary

The merged helper boundary is intentionally narrow:

- Runtime remains disabled by default.
- Runtime enablement requests return blocked metadata instead of starting a
  listener.
- Listener started remains false.
- Startup permitted remains false.
- Runtime enabled remains false.
- Responses keep raw data excluded.
- Responses keep file body data excluded.
- Responses do not include host values, credential values, target identifiers,
  stack trace bodies, or local filesystem paths.
- Output bundle structure remains the same four AI input candidate files:
  `analysis_packet.json`, `chatgpt_prompt.md`, `codex_task_prompt.md`, and
  `report_draft.md`.

## Not implemented

The following remain not implemented and not approved by this merge:

- listener startup
- socket, bind, listen, or accept behavior
- stdio runtime
- HTTP runtime
- protocol parser
- JSON-RPC parser
- request dispatcher
- executable tool registration
- tool registry runtime
- tool discovery runtime
- actual tool execution
- local evidence reader
- safe file body reader
- raw preview or raw download
- dashboard start or stop control
- upload or import action
- replay or active scan
- automatic ChatGPT handoff
- tag changes
- GitHub Release changes

## Follow-up PR split rules

Follow-up work must stay split unless a later reviewed approval explicitly
changes the boundary:

- Transport and protocol parsing stay separate.
- Protocol parsing and request dispatch stay separate.
- Tool registration, tool discovery runtime, and actual tool execution stay
  separate.
- Local evidence reading needs its own path and raw-free error boundary.
- Dashboard state-changing controls need their own action audit and CSRF review.
- Upload/import behavior stays separate from MCP listener work.
- Replay, active scan, and automatic ChatGPT handoff remain deferred.
- Tag and GitHub Release actions remain separate release actions.

## Required checks before follow-up runtime work

Before any follow-up runtime-facing PR expands beyond the two helper modules,
it must show:

- Runtime-facing files are declared in a source-check fixture.
- Forbidden marker checks cover the new files.
- Runtime flags remain false unless explicitly approved for that PR.
- Disabled and blocked responses remain raw-free.
- The four-file output bundle structure remains unchanged.
- Rollback does not move tags or mutate GitHub Releases.

## Release boundary

This note does not create or approve a v0.8 tag. It does not create or approve
a GitHub Release. Release work requires a separate explicit approval after the
target commit, release body, and release hygiene are reviewed.
