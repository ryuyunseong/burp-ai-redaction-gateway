# v0.8 Minimal Skeleton Planning

This document defines the v0.8 transport and protocol minimal skeleton
planning boundary before any skeleton runtime is implemented. It is a planning
and review-boundary document only. It does not add socket runtime, stdio
runtime, HTTP runtime, protocol parsing, JSON-RPC parsing, request dispatch,
tool registration runtime, tool discovery runtime, actual tool execution,
local evidence reading, safe file body reading, raw preview, dashboard
state-changing control, upload or import behavior, replay, active scan,
automatic ChatGPT handoff, tag changes, or GitHub Release changes.

## Purpose

- Consume the v0.8 backlog split, transport design, protocol handler design,
  protocol negative test harness, tool registration design, and read-only tool
  contract before any minimal skeleton implementation is proposed.
- Fix the disabled-by-default, raw-free, manual-review-required skeleton
  boundary before runtime-facing files are allowed.
- Keep transport, protocol parsing, request dispatch, tool registration, tool
  execution, and local evidence reading as separate approval surfaces.
- Preserve the four-file AI input candidate boundary.

## Current v0.8 baseline

The current baseline includes the published v0.7 release, v0.8 backlog split,
v0.8 transport design-only boundary, v0.8 protocol handler design-only
boundary, v0.8 protocol negative test harness, v0.8 tool registration
design-only boundary, and v0.8 read-only tool contract. The gateway can process
local Burp export or collector output through redaction, verify, review, and
report flows, then present only the existing safe output bundle for human
review.

This planning document does not change that baseline. Candidate findings
remain candidates, risk remains draft, and final severity or scoring remains
manual.

## Disabled-by-default requirements

A later minimal skeleton proposal must stay disabled by default and must show
the following before implementation is reviewed:

- The future skeleton is disabled by default.
- The future skeleton is loopback-only if any runtime is later approved.
- The future skeleton does not parse protocol messages in the same PR.
- The future skeleton does not dispatch tools.
- The future skeleton does not read local evidence.
- The future skeleton does not return file bodies.
- The future skeleton returns raw-free blocked or disabled responses.
- The future skeleton preserves manual review and the four-file safe candidate
  boundary.

## Transport/protocol separation

Transport and protocol behavior must remain separate from each other until a
later approval explicitly allows both surfaces together. A future skeleton PR
must not combine socket or transport startup with protocol parsing, request
dispatch, executable tool registration, tool discovery runtime, tool execution,
local evidence reading, raw preview, dashboard state-changing control, upload
or import behavior, replay, active scan, or automatic handoff.

## Contract consumption requirements

A later skeleton proposal must consume and cite the following planning inputs:

- v08_backlog_split.

- v08_protocol_negative_harness.
- v08_tool_registration_design.

must not add a dispatcher, executable registration, discovery runtime, actual
execution, local evidence reader, safe file body reader, raw preview, external
handoff, dashboard state-changing control, upload/import action, tag action, or
release action.

## Source-check requirements

Before any minimal skeleton runtime is allowed, runtime-facing files must be
declared in a fixture and covered by source-check tests. A future PR must fail
if those files contain forbidden markers for socket runtime, stdio runtime,
HTTP runtime, protocol parsing, JSON-RPC parsing, request dispatch, executable
tool registration, tool discovery runtime, tool execution, local evidence
reading, safe file body reading, raw preview, replay, active scan, automatic
handoff, dashboard state-changing control, upload/import behavior, tag action,
or release action without a separate reviewed approval.

## Security review requirements

Every later skeleton PR must state:

- Whether any runtime surface is implemented.
- Whether the skeleton is disabled by default.
- Whether any approved runtime is loopback-only.
- Whether protocol parsing is included.
- Whether request dispatch is included.
- Whether executable registration or tool discovery runtime is included.
- Whether actual tool execution is included.
- Whether local evidence or safe file body reading is included.
- Whether raw preview or download is included.
- Whether replay, active scan, or external handoff is included.
- Whether dashboard state-changing control or upload/import behavior is
  included.
- How blocked and disabled responses remain raw-free.
- How rollback works without moving release tags or changing GitHub Releases.

If any answer expands beyond planning, fixture, source-check, or disabled
skeleton approval, the work must be split into another PR.

## Rollback expectations

Rollback for this planning PR is a documentation, fixture, and test revert. A
later implementation PR must include its own rollback section and must not
depend on moving release tags or changing GitHub Releases.

## Deferred decisions

- Whether a disabled-by-default skeleton approval packet should be completed
  before any runtime-facing file is added.
- Whether transport and protocol skeletons should remain separate PRs.
- Whether local evidence reading should wait until a dedicated path traversal
  and raw-free error model is approved.
- Whether tool execution should remain blocked until after transport,
  protocol, registration, and dispatcher behavior are each reviewed.
