# v0.10 Scope Decision

## Purpose

This document freezes the first v0.10 planning boundary after the v0.9
safe-core release. It decides the next review path before any transport,
listener, tool execution, local evidence reader, or raw preview surface is
implemented.

## Current baseline

- Current branch baseline: `main`
- v0.9 release tag: `v0.9`
- v0.9 release target commit: `a50c66e08f9618cbc021cfbe0de0ee0a6ec8b08f`
- v0.10 decision type: scope decision only
- Manual review: required before any runtime expansion
- Raw data included: false

## v0.9 release baseline

v0.9 is a safe-core release. It includes the local redaction, verification,
review, and report workflow, the AI candidate four-file boundary, read-only
dashboard boundary work, MCP parser boundary work, read-only registry metadata,
and a minimal blocked-only dispatcher decision helper.

v0.9 does not include transport or listener runtime, executable tool
registration, actual tool execution, local evidence reading, raw
preview/download, replay or active scan, dashboard state-changing action,
upload/import action, or automatic handoff.

## v0.10 candidate directions

Candidate paths are:

- transport/listener approval packet
- transport/listener negative fixture harness
- listener startup skeleton after approval
- transport runtime skeleton after approval
- executable tool registration decision
- actual tool execution threat boundary
- local evidence reader threat boundary

## Recommended first v0.10 path

The recommended first path is `transport_listener_approval_packet`.

This keeps network-facing startup decisions separate from executable tool
registration, actual tool execution, local evidence body access, raw preview,
and state-changing dashboard or upload/import actions.

## Security boundary

Transport/listener work opens an external input boundary. Tool execution opens
an execution boundary. Local evidence reader work opens a file access boundary.
These boundaries must not be combined in one PR.

## Required approval packets

Future v0.10 work must be split into explicit packets:

- transport/listener approval packet
- listener startup negative fixture harness
- listener startup implementation decision
- transport runtime implementation decision
- executable tool registration decision
- actual tool execution threat boundary
- local evidence reader threat boundary

The listener startup negative fixture harness is tracked in
`tests/fixtures/v10_listener_startup_negative_cases.json`. It is fixture, test,
source-check, and documentation boundary work only. It does not implement
listener runtime, transport runtime, socket bind/listen/accept, protocol
handling, tool execution, local evidence reading, raw preview, replay,
state-changing dashboard controls, upload/import, or automatic handoff. A
future listener implementation PR must consume this fixture before opening a
startup surface.

The listener startup implementation decision is tracked in
`docs/V0.10_LISTENER_STARTUP_IMPLEMENTATION_DECISION.md` and
`tests/fixtures/v10_listener_startup_implementation_decision.json`. It allows
only a future listener startup skeleton step. It does not implement listener
runtime, transport runtime, socket bind/listen/accept, protocol handling, tool
execution, local evidence reading, raw preview, replay, state-changing
dashboard controls, upload/import, or automatic handoff.

## PR split requirements

The following combined PRs are blocked:

- listener plus tool execution
- listener plus local evidence reader
- transport plus raw preview
- tool execution plus local evidence reader
- upload/import plus state-changing action

The v0.10 scope decision is document, fixture, and hygiene test only. Runtime
source files must not be modified by this decision PR. Future implementation
PRs must include source checks for network, execution, file body, raw preview,
replay, and automatic handoff markers before opening any runtime surface.

evidence reading, raw preview/download, replay/active scan, dashboard
