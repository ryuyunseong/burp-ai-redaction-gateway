# v0.8 Runtime Source-Check Consumption Guard

This document defines the source-check consumption guard required before any
v0.8 runtime-facing skeleton file is added. It is a fixture, test, and
review-boundary document only. It does not implement skeleton runtime, socket
runtime, stdio runtime, HTTP runtime, protocol parsing, JSON-RPC parsing,
request dispatch, tool registration runtime, tool discovery runtime, actual
tool execution, local evidence reading, safe file body reading, raw preview,
dashboard state-changing control, upload or import behavior, replay, active
scan, automatic ChatGPT handoff, tag changes, or GitHub Release changes.

## Purpose

- Force later runtime-facing PRs to consume the v0.8 skeleton approval packet.
- Declare expected runtime-facing file names before those files exist.
- Make fixture drift, missing approval consumption, and forbidden runtime
  markers fail source-check tests.
- Keep runtime implementation blocked until explicit human approval is recorded.

## Current v0.8 baseline

The current baseline includes:

- v08_backlog_split.
- v08_transport_design.
- v08_protocol_handler_design.
- v08_protocol_negative_harness.
- v08_tool_registration_design.
- v08_read_only_tool_contract.
- v08_minimal_skeleton_planning.
- v08_skeleton_approval_packet.

This guard does not change that baseline. Candidate findings remain candidates,
risk remains draft, and final severity or scoring remains manual.

## Guard scope

This guard may define:

- Runtime-facing file declaration metadata.
- Approval packet consumption requirements.
- Forbidden marker categories.
- Source-check failure conditions.
- Required negative test categories.
- Security review and rollback expectations.

This guard may not create runtime-facing files or implement runtime behavior.

## Explicit non-goals

This guard does not implement or approve:

- Skeleton runtime.
- Socket, bind, listen, or accept behavior.
- Stdio transport runtime.
- HTTP transport runtime.
- Protocol parser.
- JSON-RPC parser.
- Request dispatcher.
- Executable tool registration.
- Tool registry runtime.
- Tool discovery runtime.
- Actual tool execution.
- Local evidence reader.
- Safe file body reader.
- Raw preview or raw download.
- Dashboard start or stop control.
- Upload or import action.
- Replay or active scan.
- Automatic ChatGPT handoff.
- Tag changes.
- GitHub Release changes.

## Runtime-facing file declaration requirements

Later runtime PRs must declare every runtime-facing file in a reviewed fixture
before implementation starts. The current expected file metadata is:

- `burp_ai_redaction_gateway/mcp_minimal_skeleton.py`.
- `burp_ai_redaction_gateway/mcp_runtime_contract.py`.

Those files are not created by this guard. If a later PR adds either file, the
PR must also show that the file is covered by source-check tests before review.

## Approval packet consumption requirements

A later runtime-facing PR must consume the approval packet and show:

- consume_v08_skeleton_approval_packet.
- explicit_human_approval_required.
- expected_base_commit_required.
- disabled_by_default_required.
- loopback_only_if_runtime_approved.
- raw_free_blocked_disabled_response_required.
- rollback_without_tag_release_mutation_required.
- four_file_safe_candidate_boundary_required.

## Forbidden marker categories

- protocol_parser.
- json_rpc_parser.
- request_dispatcher.
- executable_tool_registration.

## Source-check failure conditions

Source-check tests must fail when any of these conditions appear:

- runtime_facing_file_missing_from_fixture.
- fixture_missing_approval_packet_consumption.
- fixture_flag_drift_to_true.
- forbidden_marker_present_without_approval.
- raw_free_contract_missing.
- rollback_requirement_missing.
- tag_release_mutation_marker_present.
- output_bundle_structure_change_marker_present.

## Required negative tests

Later runtime-facing PRs must include negative tests that fail if a PR adds:

- Runtime-facing files outside the declaration fixture.
- Runtime implementation while the guard still marks implementation as false.
- Socket bind, listen, or accept markers.
- Stdio or HTTP runtime markers.
- Protocol or JSON-RPC parser markers.
- Request dispatcher markers.
- Tool registration, discovery, or execution markers.
- Local evidence or safe file body reader markers.
- Raw preview or raw download markers.
- Replay, active scan, or automatic handoff markers.
- Dashboard state-changing or upload/import markers.
- Tag or GitHub Release mutation markers.
- Output bundle structure change markers.

## Security review requirements

Every later runtime-facing PR must state:

- Which approval packet was consumed.
- Which target branch and expected base commit were reviewed.
- Whether explicit human approval was recorded.
- Whether the runtime remains disabled by default.
- Whether any approved runtime remains loopback-only.
- Whether blocked or disabled responses remain raw-free.
- Whether the four-file safe candidate boundary remains unchanged.
- Whether rollback avoids tag movement and GitHub Release mutation.

If any answer expands beyond a disabled-by-default minimal skeleton proposal,
the work must be split into another PR.

## Rollback expectations

Rollback for a later runtime PR must:

- Revert runtime-facing files without moving release tags.
- Revert runtime-facing files without changing GitHub Releases.
- Keep output bundle structure unchanged.
- Keep manual review and four-file safe candidate boundary unchanged.
- Keep blocked or disabled responses raw-free.

## Deferred decisions

- Whether the first runtime PR should create only one runtime-facing file.
- Whether transport and protocol behavior must remain in separate PRs.
- Whether local evidence reading requires a dedicated path traversal model.
- Whether tool execution stays blocked until transport, protocol, registration,
  and dispatcher behavior are each reviewed.
