# v0.8 Transport Design

This document defines the v0.8 MCP transport boundary before any transport
runtime is implemented. It is a design-only and review-boundary document. It
does not add socket binding, listener startup, stdio runtime, HTTP runtime,
protocol parsing, tool registration, tool execution, local evidence reading,
raw preview, dashboard state-changing control, upload or import behavior,
replay, active scan, automatic ChatGPT handoff, tag changes, or GitHub Release
changes.

## Purpose

- Consume the v0.8 backlog split before opening a transport surface.
- Define what a later transport PR must prove before runtime code is added.
- Keep transport separate from protocol parsing, tool registration, tool
  execution, local evidence reading, raw preview, and state-changing dashboard
  behavior.
- Preserve the four-file AI input candidate boundary.

## Current v0.7 baseline

The current baseline is the published v0.7 release plus post-release smoke and
one local-only operational smoke. The gateway can process local Burp export or
collector output through redaction, verify, review, and report flows, then
present only the existing safe output bundle for human review.

This transport design does not change that baseline. Candidate findings remain
candidates, risk remains draft, and final severity or scoring remains manual.

## Transport design scope

This PR may define:

- Transport acceptance criteria.
- Transport failure and blocked-response expectations.
- Source-check requirements for future transport-facing files.
- Negative test categories for forbidden runtime behavior.
- Review rules for later transport implementation PRs.

This PR may not add transport runtime code.

## Explicit non-goals

This design does not implement or approve:

- Socket, bind, listen, or accept behavior.
- Stdio transport runtime.
- HTTP transport runtime.
- MCP protocol handler.
- JSON-RPC parser.
- Executable tool registration.
- Actual tool execution.
- Local evidence reader.
- Safe file body reader.
- Raw preview or raw download.
- Replay or active scan.
- Automatic ChatGPT handoff.
- Dashboard start or stop control.
- Upload or import action.
- Tag changes.
- GitHub Release changes.

## Allowed future transport boundary

A later transport implementation PR may be considered only after this design is
reviewed. That later PR must stay disabled by default unless a separate
approval explicitly says otherwise, and it must not include protocol parsing,
tool registration, tool execution, local evidence reading, raw preview,
dashboard state-changing control, upload or import behavior, replay, active
scan, or automatic handoff.

Allowed future transport behavior is limited to a minimal local transport
boundary that can return raw-free metadata and blocked responses. Any payload
body handling, protocol interpretation, tool call dispatch, safe file body read,
or external handoff remains outside the transport PR.

## Forbidden transport behaviors

The transport design keeps the following behaviors blocked:

- Opening sockets or accepting connections.
- Starting stdio transport runtime.
- Starting HTTP transport runtime.
- Parsing MCP protocol messages.
- Parsing JSON-RPC requests.
- Registering executable tools.
- Dispatching or executing tools.
- Reading local evidence or safe file bodies.
- Previewing or downloading raw data.
- Starting or stopping dashboard services.
- Uploading, importing, replaying, or actively scanning traffic.
- Sending output automatically to ChatGPT or other external systems.

## Required negative tests

Any later implementation PR must include negative tests or source checks that
fail if the PR adds:

- Socket bind, listen, or accept markers.
- Stdio or HTTP runtime startup.
- Protocol parser or JSON-RPC parser markers.
- Tool registration or execution markers.
- Local evidence reader or file body reader markers.
- Raw preview or raw download markers.
- Dashboard state-changing action markers.
- Upload, import, replay, active scan, or automatic handoff markers.

Blocked and failure responses must remain raw-free and must not echo sensitive
input values.

## Source-check requirements

Before transport runtime is allowed, the transport-facing file list must be
declared in a fixture and covered by source-check tests. A future PR must fail
if a transport-facing file contains forbidden markers for protocol handling,
tool registration, tool execution, local evidence reading, raw preview,
dashboard state-changing controls, upload or import actions, replay, active
scan, or automatic handoff.

## Security review requirements

Every later transport PR must state:

- Whether any runtime surface is added.
- Whether transport is disabled by default.
- Whether any protocol parsing is included.
- Whether any payload body handling is included.
- Whether any local file or evidence reading is included.
- Whether any external network behavior is included.
- Whether any state-changing API is included.
- How blocked responses remain raw-free.
- How rollback works without moving release tags.

If any answer expands beyond transport metadata or disabled-by-default runtime,
the work must be split into another PR.

## Rollback expectations

Rollback for this design-only PR is a documentation and fixture revert. A later
transport implementation PR must include its own rollback section and must not
depend on moving release tags or changing GitHub Releases.

## Deferred decisions

- Whether transport should start as design-only for another PR before any
  disabled runtime skeleton is added.
- Whether stdio and HTTP transport should stay in separate PRs.
- Whether transport should be tested only through source checks before a later
  runtime smoke plan exists.
- Whether protocol handler design should immediately follow this PR or wait for
  a transport negative test harness.
