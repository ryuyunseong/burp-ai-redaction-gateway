# v0.9 Dispatcher Approval Packet

This approval packet fixes the dispatcher boundary before any dispatcher
implementation starts. It is documentation, fixture, and negative-test planning
only. It does not implement dispatcher invocation, executable tool
registration, actual tool execution, listener startup, transport runtime, or
local evidence reading.

## Purpose

- Define the future dispatcher input boundary after parser metadata exists.
- Define the future dispatcher output boundary before dispatcher code exists.
- Define raw-free blocked response requirements for dispatcher-denied cases.
- Define audit boundaries before dispatcher activity can be recorded.
- Keep dispatcher work separate from executable registration, tool execution,
  local evidence reading, listener startup, and transport runtime.

## Dispatcher Input Boundary

Future dispatcher input may accept only parser metadata that has already passed
the parser boundary. Dispatcher input must not include:

- raw request or response content
- credential, token, or session values
- actual target identifiers
- actual URL, domain, or IP values
- full local paths
- local evidence bodies
- safe file bodies
- tool execution results
- callback handles
- handler names
- command strings

Parser implementation and dispatcher implementation must remain separate PRs.
The dispatcher must not become the first component to parse untrusted protocol
input.

## Dispatcher Output Boundary

Future dispatcher-denied responses may include only:

- `status`
- `reason_code`
- `dispatcher_approved`
- `dispatcher_invocation_allowed`
- `tool_execution_allowed`
- `raw_data_included`
- `manual_review_required`
- `safe_message`

Future dispatcher-denied responses must not include:

- `tool_result`
- `evidence_body`
- `raw_body`
- `local_file_path`
- `target_identifier`
- `credential_value`
- `stack_trace`
- `callback_handle`
- `command`
- `handler_name`

Every dispatcher-denied response must set `dispatcher_approved` to false,
`dispatcher_invocation_allowed` to false, `tool_execution_allowed` to false,
`raw_data_included` to false, and `manual_review_required` to true.

## Blocked Response Requirements

Blocked dispatcher responses must use safe metadata only. The response must not
echo original parser input, untrusted method labels, raw bodies, credential
values, target identifiers, local paths, handler names, callback handles, or
command strings.

The safe message should be generic enough for user-facing review while avoiding
implementation details or sensitive values.

## Audit Boundary

Future dispatcher audit records must remain raw-free. Audit metadata may record
only synthetic labels, boolean boundary flags, reason codes, status labels, and
manual-review flags.

Audit metadata must not include raw traffic, target identifiers, credential
values, full paths, local evidence bodies, file bodies, callback handles,
handler names, command strings, or tool execution results.

## Required Negative Tests

Future dispatcher implementation must be blocked until tests cover:

- `dispatcher_approval_false`
- `dispatcher_invocation_false`
- `tool_execution_absent`
- `executable_registration_absent`
- `local_evidence_reader_absent`
- `raw_input_rejected`
- `credential_input_rejected`
- `target_identifier_input_rejected`
- `local_path_input_rejected`
- `audit_raw_free`
- `output_allowed_fields_only`

These tests belong to a future dispatcher implementation PR or a dedicated
dispatcher negative harness PR. They are not implemented by this approval
packet.

The dispatcher negative fixture harness is tracked in
`tests/fixtures/v09_dispatcher_negative_cases.json`. It records synthetic
blocked and denied case expectations only. It does not implement dispatcher
invocation, executable tool registration, actual tool execution, local evidence
reading, safe file body reading, listener startup, or transport runtime. Any
future dispatcher implementation PR must consume this fixture before adding
dispatcher behavior.

The dispatcher implementation decision is tracked in
`docs/V0.9_DISPATCHER_IMPLEMENTATION_DECISION.md` and
`tests/fixtures/v09_dispatcher_implementation_decision.json`. It defines the
candidate implementation scope, required fixture consumption, output boundary,
blocked response boundary, audit boundary, and source-check requirements for a
future dispatcher implementation PR. It does not implement dispatcher behavior.

## Source-check Requirements

Source-check scope for this packet is limited to documentation, fixture, and
hygiene-test changes. No dispatcher implementation file is added by this
packet.

Future dispatcher implementation PRs must add dedicated source-check coverage
before introducing dispatcher source files. Until then, implementation markers
for dispatching, executable registration, tool execution, local evidence
reading, file body reading, raw preview, replay, active scan, handler names,
callback handles, command strings, listener startup, and transport runtime must
remain absent from runtime code added by dispatcher work.
