# v0.6.1 Hotfix Triage

This document defines how to monitor and triage possible `v0.6.1` hotfix
work after the `v0.6` release. It is triage guidance only. It does not change
runtime behavior, collector forwarding, receiver ingest, dashboard actions,
MCP behavior, redaction rules, HMAC behavior, CSRF behavior, retention
behavior, tags, or GitHub Releases.

## Purpose

- Keep post-release issues focused on reproducible `v0.6` regressions.
- Separate hotfix candidates from v0.7 feature work.
- Keep release notes, PR bodies, and triage notes raw-free.
- Prevent MCP runtime work from being treated as a patch release item.

## v0.6 Release Baseline

The `v0.6` release baseline is the published local-first workflow for:

- Local redaction.
- Verify.
- Review.
- Report.
- Simple Dashboard operator checks.
- Four-file AI input candidate output bundle.
- Release readiness evidence and approval packet documentation.

The release baseline does not include MCP server listener implementation,
transport implementation, protocol handler implementation, executable tool
registration, actual tool execution, local evidence reader implementation,
raw preview, raw download, replay, active scan, or automatic ChatGPT handoff.

## Hotfix Candidate Criteria

A `v0.6.1` hotfix candidate must be narrow, reproducible, and release-related.
Acceptable candidates include:

- Reproducible error discovered after the `v0.6` release.
- Error that blocks the redaction, verify, review, or report flow.
- Clear Simple Dashboard copy-only display error.
- Regression in creating or displaying the four-file output bundle.
- Broken release body wording, README link, or documentation link.
- Documentation hygiene issue that affects Gitleaks or git safety results.

A candidate remains triage-only until reproduction evidence and affected-area
verification are available.

## Not A Hotfix

The following must not be included in `v0.6.1` hotfix scope:

- MCP server listener implementation.
- MCP transport implementation.
- MCP protocol handler implementation.
- Executable tool registration.
- Actual tool execution.
- Local evidence reader implementation.
- Safe file body reader implementation.
- Raw preview or raw download.
- Replay or active scan.
- Automatic ChatGPT handoff.
- Output bundle four-file structure change.
- Large refactor.
- New UX feature.
- v0.7 scope work.

These items require separate planning and security review before
implementation.

## Required Reproduction Evidence

Each hotfix candidate should record only raw-free metadata:

- Release version or tag.
- Affected command, document, or read-only route alias.
- Short symptom summary.
- Minimal reproduction step summary.
- Expected result.
- Actual result summary.
- Whether the four-file output bundle was affected.
- Whether redaction, verify, review, or report was blocked.
- Whether release notes or README wording was affected.

Do not record raw traffic, actual target identifiers, credential values,
personal data, full local path details, local-only evidence filenames, raw
audit rows, archive content, or stack trace bodies.

## Required Security Checks

Before a hotfix candidate can move to implementation, confirm:

- The issue is reproducible without recording raw values.
- The proposed fix does not add a new feature.
- Candidate finding wording remains candidate-only.
- Draft risk wording remains draft-only.
- Draft report wording remains visible.
- Severity and CVSS remain manual decisions.
- The four-file output bundle remains unchanged unless a separate release
  plan explicitly approves a structure change.
- The affected-area gate is identified before coding starts.
- Secret scanning remains part of the verification path.

## Required Release Note Impact Check

Before merging a hotfix, decide whether release notes or README wording need a
follow-up patch. The release text must remain raw-free and must not imply:

- Sharing approval.
- Issue confirmation.
- Severity certainty.
- CVSS certainty.
- MCP runtime availability.
- Automatic ChatGPT handoff availability.

## Branch Naming Rule

Use this branch pattern for a hotfix candidate:

- `hotfix/v0.6.x-<short-topic>`

Each hotfix branch should contain one reproducible bug or one documentation
correction with its directly related test update. Do not combine unrelated
issues in one hotfix PR.

## PR Size Rule

A `v0.6.1` hotfix PR should stay small:

- One bug or one documentation correction.
- One affected area.
- One regression test or hygiene test when practical.
- Release note impact stated in the PR body.
- No runtime MCP surface added.
- No new dashboard state-changing action.

If the change needs a design decision, runtime permission boundary, data
handling change, or new user workflow, move it out of hotfix scope.

## Deferred Work

The following remain deferred to v0.7 planning or a separate security-focused
PR:

- MCP listener skeleton.
- MCP transport.
- MCP protocol handler.
- Executable tool registration.
- Actual tool execution.
- Local evidence reader.
- Dashboard state-changing action.
- Raw preview or download.
- Replay or active scan.
- Automatic ChatGPT handoff.
- Large UI flow changes.

## Explicit Non-Goals

This document does not:

- Create a tag.
- Modify a GitHub Release.
- Approve a hotfix.
- Implement a hotfix.
- Implement MCP runtime behavior.
- Change capture, ingest, redaction, verification, review, report, dashboard,
  audit, archive, HMAC, CSRF, retention, or release behavior.
- Approve external sharing.
