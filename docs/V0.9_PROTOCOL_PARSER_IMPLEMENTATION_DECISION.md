# v0.9 Protocol Parser Implementation Decision

## Purpose

This decision record fixes the approval boundary before any v0.9 protocol
parser implementation starts. It consumes the approved parser packet and the
negative fixture harness, but it does not implement parser behavior.

## Current Baseline

- main HEAD: `5a2dc00e78e88fcd855bcee7c781abf520108311`
- PR #137 merge commit: `5a2dc00e78e88fcd855bcee7c781abf520108311`
- protocol parser approval packet: merged
- protocol parser negative fixture harness: merged
- v0.9 tag: not created
- GitHub Release v0.9: not created

## Implementation Decision Status

Protocol parser implementation remains pending explicit approval. This
decision record only defines the smallest acceptable future implementation
candidate and the boundaries that must stay outside that candidate.

## Allowed Implementation Candidate

After explicit approval, the only allowed first implementation candidate is a
minimal parser function that:

- consumes `tests/fixtures/v09_protocol_parser_negative_cases.json`
- returns blocked responses for malformed input
- emits only the allowlisted blocked response fields
- never echoes raw input
- never echoes credential, session, or token values
- never echoes target identifiers
- never echoes local paths
- sets `parser_approved` to false for all negative cases
- sets `raw_data_included` to false for all negative cases
- sets `manual_review_required` to true for all negative cases

## Forbidden Scope

The implementation decision does not approve:

- dispatcher implementation
- executable tool registration
- actual tool execution
- local evidence reader
- safe file body reader
- listener startup
- transport runtime
- raw preview or download
- replay or active scan
- automatic ChatGPT handoff
- output bundle structure changes
- v0.9 tag creation
- GitHub Release v0.9 creation

## Negative Fixture Consumption

Any future parser implementation PR must consume
`tests/fixtures/v09_protocol_parser_negative_cases.json`. The implementation
must keep the fixture categories, blocked response field allowlist, and
echo-forbidden classes aligned with
`tests/fixtures/v09_protocol_parser_approval_packet.json`.

## Required Tests

The first implementation PR must prove that:

- all eleven negative fixture categories are blocked
- every negative case returns `parser_approved=false`
- every negative case returns `raw_data_included=false`
- every negative case returns `manual_review_required=true`
- blocked responses include only allowlisted response fields
- forbidden echo classes are not reflected in responses
- dispatcher, tool execution, and local evidence reader code remains absent

## Source-check Requirements

Before any parser implementation is merged, source checks must confirm that the
parser PR does not add dispatcher, tool execution, local evidence reader,
listener startup, transport runtime, raw preview, or automatic handoff markers.

## Rollback Expectation

If a future implementation PR expands beyond the allowed candidate, the parser
implementation must be reverted or split until only the minimal parser function
and its negative tests remain. This decision record and its fixture can stay as
the planning baseline unless their boundaries are found to be incorrect.

## Explicit Approval Requirement

This decision record does not authorize implementation by itself. A future PR
that starts parser implementation needs explicit approval and must keep
dispatcher, tool execution, listener, transport, and local evidence reader work
separate.

## Positive Shape Follow-up

The positive parser output shape is tracked separately in
`docs/V0.9_PARSER_POSITIVE_SHAPE_DECISION.md`. That decision is planning only:
it fixes the allowed future read-only structured parse metadata fields before
any positive parser implementation, and it does not approve dispatcher, tool
execution, listener, transport, or local evidence reader behavior.
