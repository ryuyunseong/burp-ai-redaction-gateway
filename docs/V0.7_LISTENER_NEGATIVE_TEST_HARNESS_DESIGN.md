# v0.7 Listener Negative Test Harness Design

This document fixes the negative-test harness design for a future minimal
listener runtime implementation PR. It is documentation, fixture, and test
scope only. It does not implement listener runtime behavior, socket behavior,
transport, protocol handling, executable tool registration, actual tool
execution, local evidence reading, safe file body reading, raw preview, replay,
active scan, dashboard state-changing control, upload or import action, or
automatic ChatGPT handoff.

## Purpose

- Define the blocked and disabled behavior that must fail safely before any
  minimal listener runtime implementation can be reviewed.
- Keep listener runtime separate from transport, protocol handling, executable
  tool registration, actual tool execution, local evidence reading, and
  dashboard state-changing controls.
- Require local-only, loopback-only, disabled-by-default, raw-free blocked
  responses for a later runtime implementation.
- Keep the `v0.6` tag, GitHub Release `v0.6`, and four-file AI input candidate
  output bundle unchanged.

## Harness Scope

This harness design records the negative tests that a later minimal listener
runtime implementation PR must satisfy. It does not approve or implement that
later runtime.

The harness scope is limited to:

- This is documentation, fixture, and test scope only.
- Required negative-test names.
- Expected blocked and disabled response metadata.
- raw-free blocked and disabled responses.
- Source-check expectations.
- Security review checklist.
- PR split requirements.
- Rollback and disablement expectations.
- Deferred runtime work.

These tests belong in the later runtime implementation PR. This PR only fixes

## Expected Blocked Responses

Blocked or disabled responses in a later runtime implementation must:

- Use stable `blocked` or `disabled` status codes.
- Set `raw_data_included` to `false`.
- Set `manual_review_required` to `true`.
- Avoid caller body echo.
- Avoid echoing caller-provided body values.
- Avoid target identifiers.
- Avoid URL values.
- Avoid IP address values.
- Avoid credential values.
- Avoid local path values.
- Avoid stack trace body content.
- Avoid safe file body preview content.

Reason codes must be stable allowlisted values and must not include
caller-provided text.

## Security Review Checklist

Before a later minimal listener runtime PR is approved, reviewers should
confirm:

- The listener is local-only.
- The listener is loopback-only.
- The listener is disabled by default.
- Remote bind behavior is blocked.
- Non-loopback host behavior is rejected.
- Protocol messages are rejected until a separate protocol PR exists.
- No transport implementation is included.
- No executable tool registration is included.
- No actual tool execution is included.
- No local evidence reader is included.
- No safe file body reader is included.
- No raw preview or raw download is included.
- No replay or active scan is included.
- No automatic ChatGPT handoff is included.
- No dashboard state-changing control is included.
- No upload or import action is included.
- Blocked and disabled responses are raw-free.
- The four-file AI input candidate output bundle is unchanged.
- `v0.6` tag and GitHub Release `v0.6` are unchanged.

## PR Split Requirements

The following must remain separate PRs:

- Minimal listener runtime implementation.
- Socket bind, listen, or accept behavior.
- Transport or protocol handler.
- Executable tool registration.
- Actual tool execution.
- Local evidence reader.
- Safe file body reader.
- Raw preview or raw download.
- Dashboard state-changing action.
- Upload or import action.
- Automatic ChatGPT handoff.

Each later PR must state whether it changes runtime behavior, input handling,
local file access, audit behavior, output bundle structure, or release state.

## Rollback and Disablement Expectations

A later minimal listener runtime implementation must include:

- Disabled-by-default behavior.
- A documented disablement path.
- Raw-free blocked and disabled responses.
- A rollback plan that removes the listener runtime without changing the
  four-file AI input candidate output bundle.
- No release action unless separately approved.

This design does not create the disablement mechanism. It only records that the
later runtime implementation must provide one.
