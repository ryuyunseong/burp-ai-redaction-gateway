# v0.9 Runtime Scope Decision

This document is a planning-only decision record for the next MCP phase after
the v0.8 boundary/helper release. It does not implement runtime behavior, does
not start a listener, does not parse protocol messages, does not dispatch
requests, does not execute tools, does not read local evidence, and does not
create or modify any tag or GitHub Release.

## Purpose

- Record the v0.8 completed baseline before any v0.9 runtime discussion.
- Choose the safest first v0.9 approval path before opening MCP runtime
  surfaces.
- Keep listener, transport, protocol parsing, dispatch, tool registry, tool
  execution, and local evidence reading split into separate PRs.
- Keep the four-file AI input candidate boundary unchanged.
- Keep raw-free and manual-review-required language in every future runtime
  approval path.

## Decision Scope

v0.9 should decide the first real runtime-adjacent approval path without
implementing the runtime itself. The decision scope is limited to:

- documenting candidate v0.9 start points
- comparing security risk by runtime surface
- fixing split rules before implementation
- defining negative tests required before implementation
- defining source-check requirements for future PRs
- keeping local evidence reading deferred

## v0.9 Candidate Options

### Option A: Protocol Parser Approval Packet First

Start with a protocol parser approval packet and negative-test requirements.
This remains design and fixture work only. It defines malformed input classes,
blocked-response fields, echo-forbidden value classes, and parser source-check
markers before parser implementation.

Security risk:

- lower immediate runtime risk because no listener or transport is opened
- useful for fixing malformed message boundaries before any runtime endpoint
- still sensitive because parser wording can later affect dispatch behavior

Test requirements:

- malformed input category fixture
- blocked-response field allowlist
- echo-forbidden value checks
- parser forbidden-source marker checks
- raw-free hygiene checks

### Option B: Transport And Listener Approval Packet First

Start with a transport/listener approval packet. This remains planning only. It
defines how a future listener would be disabled, loopback-scoped, and
source-checked without adding listener startup.

Security risk:

- higher than Option A because listener and transport are closer to runtime
- must avoid implying socket startup approval
- must keep protocol parsing and dispatch separate

Test requirements:

- disabled-by-default fixture
- listener-startup forbidden marker checks
- transport marker checks
- rollback requirements
- no external network behavior checks

### Option C: Read-only Tool Registry Contract First

Start with a read-only tool registry contract. This remains metadata-only. It
defines candidate tool names, blocked tool concepts, and safe response fields
without registering executable tools.

Security risk:

- lower than listener runtime if it stays metadata-only
- risk rises if registry metadata is treated as executable registration
- must stay separate from dispatch and execution

Test requirements:

- allowed tool metadata fixture
- forbidden tool concept fixture
- blocked response schema checks
- executable registration marker checks
- execution marker checks

### Option D: Local Evidence Reader Deferred

Keep local evidence reader work deferred until a dedicated threat-boundary PR.
This path protects the file and raw-data boundary from being coupled with
runtime, parser, registry, or dispatch work.

Security risk:

- highest if combined with runtime because local file access can cross raw-data
  and path boundaries
- should not begin until parser, dispatch, and tool boundaries are separately
  reviewed

Test requirements:

- dedicated threat model
- allowed file identity fixture
- path traversal negative tests
- safe file body boundary decision
- raw-free response checks

## Recommended First Step

The recommended first v0.9 step is Option A: protocol parser approval packet
first.

Reasoning:

- It does not open listener or transport runtime.
- It defines malformed-message handling before any dispatch path exists.
- It can produce negative tests that later listener and dispatcher PRs must
  consume.
- It keeps local evidence reading and actual tool execution deferred.

Option C can follow after Option A if the registry remains metadata-only.
Option B should wait until parser boundaries and source-check requirements are
stable. Option D remains deferred.

## Security Risk Summary

- Listener and transport increase runtime exposure and must remain separate.
- Protocol parsing can reflect malformed input if echo rules are not fixed
  first.
- Dispatcher work can accidentally become a tool execution path.
- Tool registry metadata can be mistaken for executable registration.
- Local evidence reading can cross raw-data and local-path boundaries.
- Raw preview, replay, active scan, and automatic handoff remain out of scope.

## Test Requirements

Every v0.9 runtime-adjacent PR must define or consume:

- planning-only or explicit implementation status
- raw-free blocked-response fields
- manual-review-required language
- forbidden source marker checks
- malformed input or blocked-surface negative tests
- four-file output bundle preservation
- no target identifier recording
- no credential value recording
- no local full-path recording
- rollback requirements without tag or GitHub Release mutation

## PR Split Rules

The following must stay split:

- listener and transport from protocol parser
- protocol parser from dispatcher
- dispatcher from tool execution
- read-only tool registry contract from actual tool execution
- local evidence reader from all runtime, parser, dispatcher, and registry work
- raw preview or download from local evidence reader
- dashboard state-changing action from MCP runtime work
- upload or import action from MCP runtime work
- automatic ChatGPT handoff from every v0.9 runtime path

- actual tool execution
