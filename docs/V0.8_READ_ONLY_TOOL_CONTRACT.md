# v0.8 Read-Only Tool Contract

This document defines the v0.8 read-only MCP tool contract before any tool
implementation or runtime registration exists. It is a planning and
review-boundary document only. It does not add tool implementation, executable
tool registration, tool registry runtime, tool discovery runtime, request
dispatch, protocol parsing, transport runtime, actual tool execution, local
evidence reading, safe file body reading, raw preview, dashboard
state-changing control, upload or import behavior, replay, active scan,
automatic ChatGPT handoff, tag changes, or GitHub Release changes.

## Purpose

- Consume the v0.8 backlog split, transport design, protocol handler design,
  protocol negative test harness, and tool registration design before any tool
  surface is implemented.
- Separate metadata-only read-only tool candidates from forbidden tool
  surfaces before a registry or dispatcher exists.
- Keep the four-file AI input candidate boundary unchanged.
- Keep candidate findings, draft risk, and manual final severity or scoring
  language visible before any MCP tool surface is proposed.

## Current v0.8 baseline

The current baseline includes the published v0.7 release, v0.8 backlog split,
v0.8 transport design-only boundary, v0.8 protocol handler design-only
boundary, v0.8 protocol negative test harness, and v0.8 tool registration
design-only boundary. The gateway can process local Burp export or collector
output through redaction, verify, review, and report flows, then present only
the existing safe output bundle for human review.

This contract does not change that baseline. Candidate findings remain
candidates, risk remains draft, and final severity or scoring remains manual.

## Read-only tool contract scope

This PR may define:

- Metadata-only future read-only tool candidates.
- Forbidden tool surface categories.
- Raw-free response requirements.
- Candidate-only finding and draft-risk language.
- Required negative test categories for forbidden tool names and behavior.
- Source-check requirements for later tool-facing files.

This PR may not add tool implementation or runtime registration code.

## Allowed future read-only metadata tools

The following names are future metadata-only candidates. They are contract
candidates only and are not implemented, registered, discoverable, callable, or
executable in this PR:

- gateway_status.
- verified_output_aliases.
- safe_file_inventory.
- prompt_readiness.
- report_readiness.
- triage_summary_metadata.
- workflow_status.
- troubleshooting_categories.
- release_readiness_metadata.

Each candidate must return metadata only. It must not return a raw body, local
file body, actual target identifier, credential value, session value, token
value, HMAC secret, CSRF token value, stack trace, full local path, or external
handoff payload.

## Raw-free response contract

Any future read-only metadata tool must keep responses raw-free. The contract
requires:

- no raw request or response.
- no credential value.
- no session value.
- no token value.
- no HMAC secret.
- no CSRF token value.
- no full local path.
- no actual target identifier.
- no stack trace.
- no file body.
- no external handoff.
- candidate findings only.
- risk draft only.
- final severity is manual.
- final scoring is manual.

## Candidate-only finding contract

Read-only metadata must not turn findings into confirmed issues. It may expose
counts, aliases, status labels, and readiness states only when those values are
raw-free. Finding rows remain candidates, risk remains draft, and final
severity or scoring remains a manual decision.

## Required negative tests

Any later implementation PR must include negative tests or source checks that
fail if the PR adds:

- Raw exchange lookup tool markers.
- Local evidence reader tool markers.
- Safe file body reader tool markers.
- Arbitrary file reader tool markers.
- File write, delete, or edit tool markers.
- Replay or active scan tool markers.
- External handoff tool markers.
- Automatic ChatGPT handoff markers.
- Dashboard state-changing tool markers.
- Upload or import tool markers.
- Tag or release action tool markers.

## Source-check requirements

Before any tool implementation is allowed, the tool-facing file list must be
declared in a fixture and covered by source-check tests. A future PR must fail
if a tool-facing file contains forbidden markers for raw exchange lookup, local
evidence reading, safe file body reading, arbitrary file reading, file
mutation, replay, active scan, external handoff, automatic handoff, dashboard
state-changing control, upload or import behavior, tag or release action,
request dispatch, executable registration, or actual execution without a
separate reviewed approval.

## Security review requirements

Every later tool PR must state:

- Whether any tool implementation is included.
- Whether executable registration is included.
- Whether request dispatch is included.
- Whether actual execution is included.
- Whether local evidence or safe file body reading is included.
- Whether raw preview or download is included.
- Whether replay, active scan, or external handoff is included.
- Whether dashboard state-changing control or upload/import behavior is
  included.
- How responses remain raw-free.
- How rollback works without moving release tags or changing GitHub Releases.

If any answer expands beyond design, fixture, source-check, or metadata-only
planning, the work must be split into another PR.

## Rollback expectations

Rollback for this planning PR is a documentation, fixture, and test revert. A
later implementation PR must include its own rollback section and must not
depend on moving release tags or changing GitHub Releases.
